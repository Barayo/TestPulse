## Context

Runs accumulate with no way to remove them, and archiving a project (`enrich-project-list`) only ever hides it — nothing in the schema or API can permanently remove a project's data. `add-project-rbac` (in flight alongside this change, not yet merged) established the permission-flag vocabulary this design extends: ten concrete, per-resource flags (`caseCreate`/`caseEdit`/`caseDelete`, `sectionCreate`/`sectionDelete`, `suiteCreate`/`suiteEditMembership`, `runCreate`/`runRecordResult`, `manageProject`), a union-across-roles authorization model, and — most relevantly here — a confirmation-dialog pattern (`RolesPage.tsx`'s "Reset to defaults") for destructive actions that this change reuses rather than inventing a second pattern.

A critical existing constraint this design must respect, not override: `test-authoring/spec.md`'s "Soft deletion protects run history" requirement makes case deletion (`DELETE /api/v1/cases/{id}`) a soft delete (`test_cases.deleted = true`) specifically so a run that included a case keeps showing that case's pinned content forever, even after the case is "deleted" from authoring lists. This requirement is scoped to deleting *a case while the project stays alive* — it says nothing about what happens when the whole project is destroyed, which is this change's actual target.

## Goals / Non-Goals

**Goals:**
- Let a Project Admin permanently delete a run (and its items/results) within a project they administer, without needing to archive/delete the whole project.
- Let a Project Admin permanently delete an already-archived project and everything scoped to it, reclaiming the storage entirely rather than leaving it archived forever.
- Every *manual* deletion is an explicitly-confirmed trigger, naming what's about to be destroyed before it happens.
- Let a Tenant Admin configure a single, instance-wide age threshold that automatically deletes closed runs past it — the change's original driving motivation (restored 2026-08-15 after initially scoping it out; see below).
- Let a Tenant Admin configure a single, instance-wide inactivity threshold that automatically *archives* (never deletes) a project that's gone quiet — restored 2026-08-16, after a user follow-up question surfaced it as a natural extension; see D9.

**Non-Goals:**
- No user deletion or anonymization (explicitly dropped from scope after clarifying with the user — this change is about runs and deactivated projects only).
- No *automatic deletion* of projects, ever — a whole project (and everything inside it) is a much larger, more consequential thing to destroy than one closed run; it keeps the manual archive-then-delete-separately two-step (D4) unconditionally. (Automatic *archiving* of an inactive project is now in scope — D9 — but archiving is reversible and non-destructive; this line is specifically about deletion, which stays 100% manual.)
- No per-project *retention* override — one instance-wide threshold for run deletion, not a setting every project owner can tune independently (matches `publicProjectsEnabled`'s existing instance-wide-only precedent — see D8). D9's project-level auto-archive *exemption* is a different, narrower thing — see D9 for why it doesn't reopen this non-goal.
- No retention policy based on anything other than a run's own age (e.g. "last activity," "unstarred," case-level signals) — `created_at` is the only timestamp already on every run with no extra tracking required. (D9's project auto-archive policy *does* use a real activity signal, computed at sweep time rather than tracked — this non-goal is scoped to run retention specifically, where the trade-off came out differently; see D9.)
- No deletion of individual cases/sections/suites beyond what `add-project-rbac` D11 already ships (`caseDelete`/`sectionDelete`) — and no change to case deletion's existing soft-delete behavior.
- No change to how an *active* project is archived (`PATCH /api/v1/projects/{id}` with `archived: true`, existing behavior) — deletion is a separate, additional step only available once a project is already archived.

## Decisions

### D1: Run deletion needs no schema changes — existing FK cascades already cover it

`test_run_items.run_id` and `test_run_results.run_item_id` are both already `REFERENCES ... ON DELETE CASCADE` (`apps/api/internal/db/schema.sql`). A plain `DELETE FROM test_runs WHERE id = $1` already removes every item and result scoped to that run with no orphaned rows and no schema change required. `store.RunRepo` gains a `Delete(ctx, runID) error` method; `service.DeleteRun(ctx, actor, runID)` checks the new `runDelete` permission via the existing `requirePermission`/resolver pattern (`projectIDFromRun` resolver already exists), then calls it.

### D2: Project deletion requires amending `schema.sql` in place to add cascades that don't exist yet

Unlike run deletion, most of the FK chain under `projects` was never built to cascade — `test_case_folders.project_id`, `test_cases.project_id`, `test_case_versions.case_id`, `test_suites.project_id`, `suite_cases.case_id`, and `test_runs.project_id` are all plain `REFERENCES` with no `ON DELETE` clause today (checked directly against `apps/api/internal/db/schema.sql`, not assumed). A `DELETE FROM projects` today would simply fail with a foreign-key violation the moment it hit any of these. Per pre-1.0 policy, `schema.sql` (the single source of truth — `replace-migrations-with-schema-sql` retired the old incremental-migration files) gets edited in place to add `ON DELETE CASCADE` to each of those six FKs.

**A seventh FK, found by the store-layer test for `Purge` itself (2026-08-15): `project_key_counters.project_id`.** This table wasn't in the original six-FK inventory (it's a small, per-project-per-entity-type counter row for key generation — `case`/`run`/`suite` — not a usage-scaled table), but it's still a real `REFERENCES projects(id)` with no cascade, and `Purge`'s final `DELETE FROM projects` fails against it exactly like the other six would have. Fixed the same way: `ON DELETE CASCADE` added directly. This is the kind of gap TDD against a real database (not just re-reading the migration by eye) is supposed to catch — the fix belongs in this same design decision, not treated as a separate follow-up.

This does **not** conflict with D1's soft-delete requirement for case deletion: that requirement governs deleting *one case inside a project that keeps existing* — the whole point is that the rest of the project's run history stays intact. Deleting the *entire project* is a different, strictly larger action where nothing is left to protect history *for* — every case, version, run, and result scoped to that project is being destroyed together, atomically, in one statement. The two behaviors coexist: `DELETE /api/v1/cases/{id}` stays a soft delete exactly as it is today; `DELETE /api/v1/projects/{id}` is new and is a real, cascading hard delete, gated on the project already being archived (D4).

**Alternative considered**: application-level cascading deletes (service layer deletes children in dependency order, in a transaction, without touching FK definitions). Rejected — six ordered DELETE statements in the service layer duplicate what the database already does correctly and atomically via cascade, add a real risk of getting the order wrong (e.g. deleting `test_cases` before `test_case_versions` would fail without the FK cascade anyway), and diverge from this codebase's existing pattern of expressing "deletion cascades away derived state" as schema (roles, teams, suite_cases, run_items/results all already do this at the FK level, not in Go).

### D3: Two new permission flags — `runDelete` and `projectDelete` — not folded into existing ones

Extends `add-project-rbac` D11's permission catalog from ten flags to twelve. `runDelete` is new (no run-scoped delete flag existed before this change — `runCreate`/`runRecordResult` only cover creating/executing). `projectDelete` is kept separate from the existing `manageProject` flag (rename/describe/archive) rather than folded into it: a role that can rename or archive a project is a routine, low-risk administrative capability; a role that can permanently destroy the project and every case/run inside it is a fundamentally different, much higher-consequence capability, and D11 explicitly established "concrete per-resource actions, not broad ones" as this codebase's permission-design principle — bundling the two together would be exactly the kind of over-broad flag D11 was written to move away from.

Both flags follow the mechanical pattern D11 already established end-to-end: migration column (`can_run_delete`, `can_project_delete`), `domain.Permission` consts (`PermRunDelete`, `PermProjectDelete`), `Role`/`Permissions` struct fields, `EffectivePermissions`'s `bool_or()` query, `RoleInput`/`Role` OpenAPI schema fields, `RolesPage.tsx`'s `PERMISSION_SECTIONS` (new items under the existing "Runs" and "Project" sections — no new section needed). Seeded defaults: Project Admin gets both (it already gets every other flag); Tester and Contributor get neither.

### D4: Project deletion requires the project to already be archived — enforced server-side, not just hidden in the UI

`DeleteProject` returns a validation error if `project.archived == false`, regardless of what the UI shows — the API is the actual gate, matching this codebase's consistent pattern of never trusting client-side hiding alone for anything destructive or security-relevant. This forces the two-step "archive, then (separately, later) delete" flow the user described ("if the user wants to clean a project that is no longer in use, he can remove the project") — archiving is the reversible, low-stakes first step; deletion is the deliberate, irreversible second one, and they can't be collapsed into a single action.

### D5: Confirmation reuses the `RolesPage.tsx` dialog pattern, but project deletion's dialog shows real content counts

Both new destructive actions (run delete, project delete) get a confirmation `Dialog` (the shadcn `Dialog` primitive, same as `add-project-rbac` D12's "Reset to defaults") naming the specific target before anything happens — "Delete run 'Sprint 12'?" / "Delete project 'Legacy QA'?". For project deletion specifically, the dialog also shows the project's suite/case count (`GET /api/v1/projects/summaries`, per D7 below no longer filtered to non-archived projects) so the confirming admin sees the actual scale of what they're about to destroy, not just its name — the user's own framing ("the target should be confirmed by the cleaning actor") implies confirming *what* is being removed, not just clicking through a generic warning.

**Concrete placement (Pepe review, 2026-08-15):**
- **Archived state**: an `Archived` `Badge variant="outline"` on `ProjectsPage.tsx`'s cards (same slot/order as the existing `Sample` badge — Sample first, Archived second) and on `ProjectPage.tsx`'s `<h1>`, before the switcher chevron. `outline` matches `RunPage.tsx`'s existing treatment for a `closed` run — a neutral lifecycle marker, not a warning. No new filter chip, no re-sort, no separate section.
- **Archive / Unarchive**: a `Switch` on `ProjectSettingsPage.tsx`, in its own `Card` below the existing "Public access" card, same row-between + On/Off shape. Label text reads "Active"/"Archived" (domain vocabulary), not generic On/Off.
- **Delete project**: a separate `Card` on `ProjectSettingsPage.tsx`, below Archive — present only when `project.archived === true` (absent, not disabled, on an active project — D4), and independently gated on `projectDelete` (reaching Settings only requires `manageProject`, per D3's flags-stay-separate principle). Its dialog: title `Delete "{name}"?`; body shows suite/case counts using the same inline-spinner loading idiom `RolesPage.tsx`'s role-deletion preview already uses, plus a filled `callout-muted` panel (not a bordered box — matches this app's existing hairline-divider-anti-aliases finding) stating deletion is asynchronous and the project disappears from lists immediately; confirm button disabled until counts resolve.
- **Delete run**: lives in `RunPage.tsx`'s header action cluster, directly beside `Reopen`, `variant="destructive"` — not on `RunsPage.tsx`'s row list, which is deliberately minimal (name/pass-rate/timestamp) and would need restructuring to fit a delete affordance per row. Gated on its own `runDelete` flag. Dialog needs no preview fetch — the run's item/result count is already on-screen from state `RunPage.tsx` already loads.

### D7: Two prerequisite fixes surfaced while designing D5, folded into this change's scope

**Unarchive.** `Service.UpdateProject` today only acts when `upd.Archived != nil && *upd.Archived` — sending `archived: false` is accepted and silently does nothing (`ProjectRepo.Archive` only ever sets `true`; there is no symmetric method). D4's "archive is the reversible, low-stakes first step" framing assumes a real unarchive path exists. This change adds `ProjectRepo.Unarchive` (mirrors `Archive` exactly: `UPDATE projects SET archived = false WHERE id = $1`) and updates `UpdateProject` to branch on the value of `*upd.Archived` rather than only checking truthiness, auditing `"archive"`/`"unarchive"` distinctly. No new permission flag — reuses `manageProject`, the same flag that already gates the existing archive path.

**`Summaries()` stops excluding archived projects.** `ProjectRepo.Summaries` currently queries `WHERE NOT archived` (`store/projects.go`). This was invisible before this change because nothing showed archived projects anywhere; the moment the D5 badge makes them visible, two things break without this fix: (1) the delete-project dialog's own count display, which specifically needs data for a project that *is* archived, would show 0/0; (2) `ProjectsPage.tsx`'s existing card-grid summary merge (`GET /api/v1/projects`, which does *not* filter archived, merged with `GET /api/v1/projects/summaries`, which does) would silently render a truthfully-wrong "0 suites · 0 cases" on every archived card. The fix is to drop the `WHERE NOT archived` filter — nothing today relies on archived projects being excluded from summaries; `domain.ProjectSummary` and the OpenAPI `ProjectSummary` schema both gain an `archived bool` field so the frontend can badge correctly from the same response `useProjectSummaries.ts` already fetches, rather than a second round trip.

### D6: Project deletion runs asynchronously, via an in-process background worker doing chunked batch deletes

A single `DELETE FROM projects WHERE id = $1` relying purely on D2's cascade is correct but risky at scale: for a project with a large run/result history, cascading through potentially millions of rows in one statement means one giant transaction (WAL/replication pressure, table bloat) and one HTTP request that can hang well past any reasonable timeout. Project deletion — unlike run deletion (D1, which stays a single synchronous statement; run-scoped data is bounded and small) — needs to handle "large" as a real case, not a hypothetical.

`projects` gains a nullable `deleting_at timestamptz` column. `DELETE /api/v1/projects/{projectId}` validates permission and the archived precondition (D4), sets `deleting_at = now()`, and returns **202 Accepted** immediately — the project is hidden from every listing endpoint from that instant (`WHERE deleting_at IS NULL` added to existing project queries), regardless of how long the actual purge takes. A background worker — a goroutine started at server boot, not a separate deployable, so this stays within the modular-monolith constraint — polls for projects with `deleting_at IS NOT NULL` and, for each, chunk-deletes the tables whose size scales with usage (`test_run_results`, `test_run_items`, `test_runs`, `test_case_versions`, `test_cases`) in batches (e.g. `DELETE ... WHERE id IN (SELECT id FROM ... LIMIT 1000)`, looped until zero rows affected), then issues the final `DELETE FROM projects WHERE id = $1` — at that point remaining child rows (sections, suites, suite_cases, membership rows) are small/bounded by project setup rather than execution volume, so D2's FK cascade cleans them up in that one closing statement without needing its own batching.

**Resumability**: the worker's batch loop is naturally idempotent — deleting already-gone rows is a no-op — so if the server restarts mid-deletion, worker startup re-scans for any project with `deleting_at IS NOT NULL` and simply resumes the same loop. No separate job-queue table, no dead-letter handling, no retry-count bookkeeping: "still has `deleting_at` set and still has child rows" *is* the resumability state.

**UI implication**: the confirmation dialog (D5) states that deletion runs in the background and may take a few minutes for large projects. Once confirmed, the project disappears from the list immediately (via `deleting_at IS NULL` filtering) — there is no progress bar or status-polling endpoint in v1; that's added scope beyond what a rare, admin-triggered, fire-and-forget action needs.

**Alternatives considered**:
- **Fully synchronous, but chunked within the request.** Rejected — chunking avoids the single-giant-transaction problem but a large project can still make the request run for minutes, which is poor practice regardless of whether the DB survives it (proxies/load balancers/browser tabs all have their own timeouts).
- **External job queue / separate worker process** (e.g. a dedicated cleanup service the user's original framing suggested). Rejected — this is the first background-processing need in the codebase, and a separate deployable directly conflicts with the standing "one Go binary" architecture constraint; an in-process goroutine gets the same async benefit with none of the new-infra cost.
- **Soft "trash" state with a separate scheduled purge job.** Considered (mirrors common "30-day trash" UX elsewhere) but rejected for *project* deletion specifically — no-undo is already an accepted trade-off below, and this is a distinct concept from D8's age-based run retention: a trash bin adds a recovery window to a deliberate manual trigger, where D8 is the trigger itself, automated. Adding both would be solving two different problems with the same shape purely for symmetry.

### D8: Automatic run retention — one instance-wide age threshold, off by default, a second independent worker (2026-08-15, restored scope)

The user's original framing for this whole change was a **customizable cleanup system for very old runs** — the manual-deletion-only design that shipped first (D1-D7) dropped that entirely (see the now-revised Non-Goals). Restoring it:

**Configuration shape.** `instance_settings` gains one field: `run_retention_days integer DEFAULT 0 NOT NULL` — `0` means the policy is off (the default; nothing is auto-deleted on a fresh instance), any positive integer is the age threshold in days. Tenant-Admin-only, alongside the existing `public_projects_enabled` switch, via the same `PATCH /api/v1/instance-settings` endpoint (gains a second optional field) — plumbing a brand-new endpoint just for this would duplicate the whole "instance settings" concept for no reason. A companion `GET /api/v1/instance-settings` (new — nothing needed to read the full settings row before; the public `/meta` endpoint only ever exposed the one field clients needed) lets `InstanceSettingsPage.tsx` show the current threshold on load, not just after saving.

Rejected: nullable column (`NULL` = off) — needs a `*int` in Go and a `null`-vs-`0`-vs-absent distinction in the PATCH body for no real benefit; `0` is already an impossible real threshold (an actual "delete everything the instant it closes" policy makes no sense), so repurposing it as the off-switch avoids the extra type complexity entirely. Rejected: per-project override — the user asked for *a* retention system, not a matrix of them; one instance-wide number matches `publicProjectsEnabled`'s existing precedent and can always grow a per-project layer later if it's actually needed.

**Eligibility.** A run qualifies for automatic deletion only if **both** are true: `status = 'closed'` and `created_at < now() - (run_retention_days || ' days')::interval`. Open runs are never touched automatically, at any age — a run being open means someone may still be actively working it; auto-deleting it out from under them is a correctness/trust problem, not just a surprising UX moment. `created_at` (not "last activity," which nothing in the schema tracks today) is the only signal available without adding new tracking machinery — re-deriving one is explicitly out of scope (see revised Non-Goals).

**Mechanism: a second, independent background worker (`RunRetentionWorker`), not an extension of `ProjectDeletionWorker`.** The two workers solve genuinely different problems — one drains a small, explicitly-marked queue (`deleting_at IS NOT NULL`) as fast as it can; the other periodically re-scans the *entire* closed-run population against a threshold that can change at any time via the settings page. Folding them into one loop would mean every project-purge tick also pays the cost of a full run-eligibility scan, and vice versa, for no shared benefit. `RunRetentionWorker.Sweep(ctx) (deleted int, err error)` is the deterministic, directly-testable unit (mirrors `ProjectDeletionWorker.ProcessPending`'s own shape): read settings, no-op if `RunRetentionDays == 0`, else list eligible runs (`RunRepo.ListEligibleForRetention`) and delete each exactly the way a manual `DeleteRun` call would (`RunRepo.Delete` — no new deletion path, reuses D1's existing cascade). `Run(ctx)` wraps `Sweep` in a ticker loop, same `Interval` pattern `ProjectDeletionWorker` already established, but a longer production default (an hour, not `ProjectDeletionWorker`'s five seconds) — this isn't draining a user-triggered queue that should feel responsive; it's routine housekeeping with no one waiting on it. Both workers start as separate goroutines at server boot, both stop on the same signal-cancelled context.

**Audit needs a real actor, not a silent gap.** `s.audit` is a no-op when no `Actor` is resolved into `ctx` — true for every call site so far because they're all mid-HTTP-request. The sweep runs with no request behind it at all. Rather than accept "runs vanish with zero audit trail when auto-deleted" (a real regression against this codebase's own "every mutating operation... capturing the acting actor" principle), `domain.ActorKind` gains a third value: `system`. The sweep constructs `domain.Actor{Kind: ActorKindSystem, ID: "retention-worker", DisplayName: "Automatic retention policy"}`, injects it via the existing `domain.WithActor` before calling `s.audit(ctx, "delete", "run", id)` — reuses the exact audit mechanism every other deletion already goes through, no parallel code path. `audit_log.actor_kind`'s CHECK constraint (`user`/`agent` today) gains `system`; `AuditEntry.ActorKind` scanning/serialization needs no change (already a plain string-backed enum).

**Sample Project showcase**: not practically demonstrable via seed data — showing it would require backdating a seeded run's `created_at` well past whatever threshold a fresh instance ships with (the default is `0`/off, so there's nothing to demonstrate out of the box regardless), and no seed helper exists for that today. The setting itself stays fully discoverable (visible, off, clearly explained on the Instance settings page) — the same "state the limitation, don't fake it" precedent `add-change-own-password` task 8.3 and this change's own task 11.1 already established for their own untestable-via-seed cases.

### D9: Automatic project archiving — instance-wide inactivity threshold, computed activity signal, Tenant-Admin-only exemption (2026-08-16, restored scope)

Immediately after D8 shipped, the user asked a natural follow-up: could an *instance* setting drive project archiving too, with a *project-level* override so a Project Admin could opt their own project out? Pepe (design review, 2026-08-16) was asked specifically about the override shape before any of this was built, and the answer reshaped the feature significantly from what was asked.

**Configuration shape.** `instance_settings` gains `auto_archive_inactive_days integer DEFAULT 0 NOT NULL` — same `0`-means-off convention as D8's `run_retention_days`, same `PATCH /api/v1/instance-settings` endpoint (a third optional field now), same reasoning against a nullable column (D8 already rejected that trade-off; it applies identically here).

**Eligibility needs a real activity signal — unlike D8, which deliberately didn't build one.** D8's Non-Goals explicitly ruled out "last activity" for run retention because nothing tracked it and building that tracking was out of scope for *that* decision. Project archiving is a different trade-off: archiving is reversible (unlike run deletion), so a wrong call costs far less, but auto-archiving a project purely by its *creation* date would flag old-but-still-busy projects incorrectly — a much worse failure mode for archiving (which hides a project from its own team) than it would be for run deletion. Rather than add a maintained `last_activity_at` column (needing a write/trigger on every case edit, run creation, suite creation — real ongoing cost and a new failure surface for something to fall out of sync), the signal is **computed at sweep time only**, via one query per sweep pass across all eligible projects (not per-request, not N+1 — this is exactly the "compute aggregates server-side in a batch job, never client-side or on every request" principle this codebase already follows for `ProjectRepo.Summaries`/`SuiteRepo`'s pass-rate queries): the greatest of the project's own `created_at`, `MAX(created_at)` across its runs, `MAX(created_at)` across its case versions (joined through its cases), and `MAX(created_at)` across its suites. A project with no runs/cases/suites at all just falls back to its own `created_at` — a brand-new, still-empty project isn't "inactive," it's unstarted.

**Rejected: a per-project self-service override.** This was the user's original framing (a Project Admin overriding the instance default on their own project) and Pepe's review rejected it directly: the one existing instance/project two-tier setting in this codebase, `publicProjectsEnabled`/`publicAccess` (`service/instance_settings.go`'s `IsProjectPubliclyAccessible`, `settings.PublicProjectsEnabled && p.PublicAccess`), is a one-directional AND-gate — the instance flag can only *restrict* a project's own setting, never grant past it, and a project's own flag is never "inherited" from the instance, it's independently owned from the start. A literal override (Project Admin locally defeating a Tenant Admin's instance-wide policy) would be a genuinely new authorization shape with no precedent anywhere in this codebase, and a real trust problem: it hands the locally-interested actor (wants their project to stay visible) standing authority to override the globally-interested actor's (wants tenant-wide hygiene) decision, silently, with no visibility step. D8 already rejected a symmetric idea (per-project retention override) for a lighter reason (avoiding a "matrix of policies"); this rejection is stronger — it's about not inverting who's allowed to override whom.

**What ships instead: a one-way, Tenant-Admin-granted exemption.** `projects` gains `auto_archive_exempt boolean DEFAULT false NOT NULL`. Only a Tenant Admin can set it — enforced inside `Service.UpdateProject` (`actor.IsTenantAdmin`, mirroring the existing `userActor`-style in-service actor check pattern, e.g. `service.go`'s favorites-only-for-user-accounts guard), not just at the HTTP route level, since the route's own permission gate for reaching `PATCH /api/v1/projects/{key}` at all is the coarser `manageProject`. This keeps the direction consistent with `publicProjectsEnabled`: the higher authority (Tenant Admin, instance-wide) is the only one who can move a project *out* of the org-wide default; nothing project-local can move it back in on its own initiative.

**Correction found during implementation: the exemption control is Tenant-Admin-only end to end, not just its write path.** The design as first written assumed a Project Admin could at least *see* the exemption state and the instance threshold on their own project's Settings page, even though only a Tenant Admin could change it. That assumption doesn't hold: `GET /api/v1/instance-settings` is itself Tenant-Admin-only (same gate as its `PATCH`, task group 20 — nothing about the auto-archive threshold specifically needed a looser read permission when that endpoint was scoped), so a Project Admin's browser has no legitimate way to learn the current threshold at all. Rather than reopen that endpoint's permission model as unplanned scope, `ProjectSettingsPage.tsx`'s exemption line and toggle are both rendered only for `me.isTenantAdmin` — a Project Admin sees nothing about auto-archive on their project's Settings page, rather than a control that can't accurately state what policy (if any) currently applies to their project.

**Why this is deliberately not a new permission flag.** D3 established this codebase's principle of concrete, per-resource permission flags assignable via fully-custom roles — but the auto-archive exemption isn't a project-scoped *action* a role grants (like `runDelete`/`caseCreate`); it's a decision about whether an *instance-wide administrative policy* applies to one project, which is conceptually the same kind of thing as project *creation* or project *membership assignment* — both already Tenant-Admin-only regardless of what any custom role grants (`docs/test-management.md`: "Assigning project membership itself... is Tenant-Admin-only; a role with Manage Project can administer the project's settings but not reassign who's on it"). Making the exemption a custom-role flag would mean a Tenant Admin could grant a Project Admin the power to defeat the Tenant Admin's *own* future policy changes on that project — reintroducing exactly the override problem this design just rejected, just gated behind role assignment instead of being unconditional. Flagged explicitly here (per Pepe's review) as a deliberate call, not an oversight: if a real need for a finer-grained, delegatable version of this emerges later, it's new scope, not a bug in this one.

**Mechanism: a third, independent background worker (`ProjectAutoArchiveWorker`).** Mirrors `RunRetentionWorker`'s shape exactly (`Sweep(ctx) (archived int, err error)`, a `Run(ctx)` ticker loop, same `Interval` pattern, an hour by default) rather than folding into either existing worker — same reasoning as D8's own worker-count decision: this sweeps a different population (non-archived, non-exempt, non-deleting projects) against a different, independently-configurable threshold, and folding it in would make every tick pay for a scan the setting might not even have enabled. `Sweep` reads `AutoArchiveInactiveDays`, no-ops at `0`, else lists eligible projects (`ProjectRepo.ListEligibleForAutoArchive`) and archives each via the *existing* `ProjectRepo.Archive` (D7's method — no new archiving path), auditing under the same `system` `ActorKind` D8 introduced (`ID: "auto-archive-worker"`, distinct from D8's `"retention-worker"` so the two automated processes are independently attributable in the audit log) — same `action: "archive"` string a manual archive already uses, distinguished purely by `actorKind`, not a parallel action vocabulary.

**Styling deliberately does not borrow D8's destructive treatment.** Run retention's Instance Settings control uses a `ring-destructive/30` card and a `TriangleAlertIcon` warning callout because it's genuinely irreversible. Archiving is not — `test-authoring/spec.md`'s own "Project management" requirement already states archiving/unarchiving are "reversible, low-stakes actions." Auto-archive's control (same shared pill-selector component D8's control uses, extracted for reuse — Pepe review) shows a plain muted line instead ("Off — projects are never automatically archived." / "Projects inactive for N days are automatically archived. Reversible any time from the project's own Settings.") — reusing destructive styling here would overstate the actual risk and violate this codebase's own color-restraint convention (`docs/design-system.md`: color marks meaningful state, not restated hierarchy).

**Sample Project showcase**: same limitation as D8 — not practically demonstrable via seed data without backdating, and the default ships off. Unlike D8, though, the Sample Project's own age (created fresh on every instance startup) combined with a low threshold could theoretically trigger a real sweep in a demo environment if a Tenant Admin sets one — worth a one-line callout on the Instance settings page copy so nobody sets a threshold and is confused when their freshly-seeded Sample Project vanishes into archived state on the next sweep.

## Risks / Trade-offs

- **[Irreversible by construction]** There is no undo, no trash/recycle-bin state, no soft-delete-then-purge-later staging for either run or project deletion — once confirmed, the DB rows are gone. → Mitigation: this is the explicit goal (real space reclamation, not another soft flag), offset by requiring project deletion to pass through archived-first (D4) and a confirmation dialog with real counts (D5); a future change could add a trash/undo window if this proves too sharp in practice, but that's explicitly not this change's job.
- **[Six-FK edit touches the core domain tables every other table ultimately hangs off of]** — a bigger blast-radius edit than most in-place `schema.sql` amendments this codebase has done so far. → Mitigation: the change is additive at the constraint level (`ON DELETE CASCADE` only takes effect on delete, changes no existing read/write/insert behavior), and the standing verification step (full `go test ./...` plus a clean `docker compose down -v` + rebuild) is exactly the check that would catch a mistake here.
- **[`runDelete`/`projectDelete` widen the permission surface again, right after `add-project-rbac` D11 already widened it from 5 to 10 flags]** More flags is more for a Tenant Admin to reason about on the Roles page. → Mitigation: both are genuinely new, previously-impossible capabilities (not a further split of an existing one), so this is the catalog growing with real new functionality, not decomposition churn; D11's `PERMISSION_SECTIONS` grouping already scales to this (new items slot into the existing "Runs"/"Project" sections, no layout change needed).
- **[D6 introduces this codebase's first background-processing mechanism]** Every prior mutation has been synchronous request/response; a goroutine-based worker with restart-resumable state is a new category of thing to get wrong (e.g. two server replicas both picking up the same `deleting_at` project and racing). → Mitigation: TestPulse is a single-binary, single-replica deployment today (no clustering/HA in scope anywhere in the codebase), so the race case doesn't exist yet; the batch loop is idempotent by construction (re-deleting already-gone rows is a no-op), which is what makes "just resume on restart" sufficient without needing distributed locking. If multi-replica deployment is ever added, this worker would need a claim/lock step first — noted here so it isn't forgotten, not solved now.
- **[D8 is silent, automatic, and irreversible — the sharpest-edged capability in this whole change]** Unlike every other deletion here, nobody actively confirms each individual run D8 removes; setting a threshold once means every closed run that crosses it, forever, with no per-run review. A misjudged threshold (set too low, or set thinking it only affected new runs rather than everything already closed) could remove more history than intended in the very first sweep. → Mitigation: off by default (`0`) on every instance, so this can never surprise anyone who never touches the setting; the Instance settings page states plainly what the number means (closed runs only, age from creation, applies immediately to existing runs, not just future ones) before a Tenant Admin sets it; every auto-deletion is still audited (as the new `system` actor), so *what* was removed and *when* stays discoverable after the fact even though *whether* to remove it was never re-confirmed per-run.
- **[D9's exemption is coupled to the same activity-signal weakness it's meant to work around]** Without a richer activity signal than "newest of a few `created_at`-family timestamps" (no login tracking, no view/read tracking), "exempt this project" is really exempting it from a signal that can already misjudge activity in either direction — e.g. a project only ever *read*, never written to, looks identical to a truly abandoned one. → Mitigation: archiving (unlike deletion) is fully reversible with one click (`Unarchive`, D7) and non-destructive, so a wrong auto-archive is a minor annoyance, not data loss — the bar for "good enough" here is deliberately lower than D8's, and exemption exists as a real escape hatch for the cases the signal gets wrong, not a promise the signal is perfect.
- **[Three independent background workers now poll the same tables on overlapping schedules]** `ProjectDeletionWorker`, `RunRetentionWorker`, and `ProjectAutoArchiveWorker` all run as separate goroutines with their own tickers; `ListEligibleForAutoArchive`'s per-project `GREATEST`-of-four-subqueries shape is also the most expensive single query any of the three workers issues so far. → Mitigation: an hourly default interval (matching `RunRetentionWorker`) keeps this firmly in "routine housekeeping" territory, not a hot path; at TestPulse's current single-tenant, pre-1.0 scale (no deployment in this codebase manages more than a handful of projects) the query cost is negligible, and if it ever isn't, adding an index or maintaining a real `last_activity_at` column becomes a scoped follow-up with a concrete performance problem to point at, not speculative optimization now.
