## 3. Server-side group-reference resolution (TDD) — the core integrity boundary

- [x] 3.1/3.2 Wrote failing tests, then implemented `Service.resolveStepGroupRefs(ctx, projectID, steps []domain.Step) ([]domain.Step, error)` (`internal/service/service.go`). **Real design decision made here, not fully pinned down by design.md's text**: since `domain.Step` stays a flat struct (one `Action`/`Expected` pair), a single `GroupRef` entry expanding to N steps means every one of those N resolved steps is stamped with the *same* `GroupRef` (same `GroupID`/`GroupKey`/`SnapshotUpdatedAt`) — a "block" is identified post-save as a maximal contiguous run of steps sharing one `GroupRef`, not a separate wrapper type. Chosen over a discriminated-union `Steps` type (more invasive: would ripple into the JUnit importer, execution board, and every other `CaseContent.Steps` consumer) for a benefit (a structurally-distinct block marker) the staleness/detach UI doesn't actually need — a shared `GroupRef` value is sufficient for the frontend to group contiguous entries. Tests (`internal/service/step_group_resolution_test.go`) cover: no-group-refs passthrough, full expansion in place (with trailing own steps preserved), **client-supplied `Action`/`Expected` on a `GroupRef` entry is discarded and replaced with the server's real lookup** (anti-spoofing), rejection of an unknown group key, rejection of a group belonging to a different project, and `SnapshotUpdatedAt` stamped to the group's actual `UpdatedAt`.
- [x] 3.3/3.4 Wired `resolveStepGroupRefs` into `Service.CreateCase` and `Service.EditCase` (tested via the same file, through the public `CreateCase`/`EditCase` contract rather than the unexported resolver in isolation — the real, observable behavior that matters). `EditCase` now unconditionally resolves the case's `projectID` up front (previously only looked up when custom fields were present) since group-ref resolution needs it regardless. Also added and verified: editing the *source group* after a case version was saved does **not** change that already-saved version's content (immutability preserved — `TestEditingSourceGroupDoesNotChangeAnAlreadySavedCaseVersion`). Full `internal/service` suite (all pre-existing tests) re-verified green — zero behavior change for cases with no group references.
- [x] 3.5 **Real bug found by Pepe's frontend-design pass (reviewing this exact function before wiring the UI to it) and fixed via TDD, before any frontend code was written**: `resolveStepGroupRefs` unconditionally re-resolved *every* `GroupRef` entry to its group's **current live content** on every save — including a plain `EditCase` that never touched that block. This directly contradicted `design.md`/`specs/reusable-steps/spec.md`'s "staleness is surfaced, never applied silently" guarantee: saving a case for an unrelated reason (e.g. renaming it) silently pulled in whatever the referenced group looked like *right now*. The original `TestEditingCaseCanPickUpTheGroupsNewContent` had locked in this wrong behavior as if intended — replaced with `TestEditingCaseWithoutRefreshingKeepsThePreviousSnapshot` (red first, confirmed the bug), `TestEditingCaseWithAnExplicitRefreshPicksUpTheGroupsNewContent`, and `TestEditingCaseWithAGroupRefNotFoundInThePreviousVersionResolvesFresh`. **Fix** (user-approved before implementing, since it changes already-shipped/tested behavior): `resolveStepGroupRefs` now takes a `previousSteps []domain.Step` parameter (nil for `CreateCase`, the case's prior version's resolved steps for `EditCase`, fetched via `store.Cases.Get` only when `hasGroupRef(content.Steps)` is true). An incoming entry's `SnapshotUpdatedAt` is compared against the group's actual current `UpdatedAt`: a match resolves fresh (client just refreshed, or this is a brand-new reference); a mismatch means the client is knowingly resending an old, unrefreshed snapshot, so the server looks up that exact `(GroupID, SnapshotUpdatedAt)` pair in `previousSteps` (new helper `carryForwardGroupRef`) and carries that content forward unchanged rather than silently adopting the group's new content — safe because that content was itself server-resolved and persisted by this same service on a prior save, never client-supplied. No match found (e.g. a genuinely new reference) falls back to resolving fresh, the same safe default `CreateCase` always uses. Full `internal/...` suite and lint re-verified green. **Also investigated Pepe's finding #3** (nested group-in-group): already impossible — `StepGroup.Validate()` (`domain.go`) requires every one of a group's own steps to have a non-empty `Action`, and a `GroupRef`-only step always has an empty `Action`, so `CreateStepGroup`/`UpdateStepGroup` already reject it (covered by the existing `TestStepGroupValidation`'s `missingAction` case) — no code change needed.

## 8. Frontend implementation: case editor group-reference UI (TDD, after task 6 sign-off)

- [x] 8.1–8.12 Wrote 9 failing component tests covering all of: group-block rendering (contiguous run sharing one `groupRef` → one block with a range badge and the fetched group name), no staleness pill when the snapshot matches, "Update available" pill + Refresh when it doesn't, Refresh replacing the block's steps and re-stamping the snapshot, "Source group deleted" state (Detach only, no Refresh) when the group 404s, Detach converting a block to plain editable steps, "Insert shared group" (picker → appends expanded steps), "Extract as shared group" (click/Shift+Click select → dialog → POST creates the group → selection replaced with a reference), and the read-only "From shared group" caption with no interactive actions — then implemented all of it in one pass (`internal/service`-side analog already existed; this is the frontend). **Design decisions made during implementation, simpler than originally scoped**:
  - The client never keeps a group reference "collapsed" as a single unexpanded entry, even immediately after insert/extract/refresh — it always writes the *fully expanded* N steps (mirroring the server's own `resolveStepGroupRefs`) into local state right away, each stamped with the same `GroupRef`. A "block" is detected purely by grouping a maximal contiguous run of steps sharing one `groupRef.groupKey` (`toBlocks` helper) — whether that run came from a fresh client-side expansion or from loading an already-saved, server-resolved case is indistinguishable and doesn't need to be. This removed an entire class of "is this collapsed or expanded" state-tracking the original plan implied.
  - Grouping keys off `groupRef.groupKey` (always present, required in the schema), not `groupRef.groupId` (schema-optional, since it's server-set) — avoids a TS-optional-vs-required mismatch and is equally reliable in practice since the client always populates both together.
  - New `apps/web/src/components/InsertStepGroupDialog.tsx` (reuses `AssignDialog`'s search-and-pick shape exactly, per Pepe) and `ExtractStepGroupDialog.tsx` (name input + read-only preview of the selected steps' text) as separate small files; the group-block rendering itself (healthy/stale/deleted states, staleness callout, Detach/Refresh) stays inline in `CaseStepsList.tsx` as a `GroupBlock` subcomponent, since it's tightly coupled to the parent's block-detection and step-array-splicing logic.
  - Selection for extraction: click a plain step's badge to toggle it (becomes the anchor); Shift+click extends a contiguous range from the anchor, but only if every index in that range is a plain step — if the range would cross a group block, it falls back to toggling just the clicked step (a simple, robust clamp rather than partial-range computation), matching `FolderExplorerPage.tsx`'s existing shift+click idiom and its `ring`/selected-row treatment (adapted to `bg-primary/5` and a filled badge here, matching a per-step badge rather than a per-row treatment).
  - `CaseStepsList` gained `projectKey?` (enables Insert/Extract/Refresh/Detach — omitted entirely by the Shared Steps admin card's own "bare" step editor, where a group's own steps can never reference another group) and `bare?` (skips the `Card` wrapper). `CaseFormatEditor`, `CreateCasePage`, `CaseDetailPage` (both edit and read-only view via `CaseContentView`), and `RunItemDetailPage` (read-only, pinned version) all thread `projectKey` through.
  - Full web test suite for every touched file (`CaseStepsList`, `CaseFormatEditor`, `CreateCasePage`, `CaseDetailPage`, `RunItemDetailPage`, `CaseContentView`) re-verified green (153 tests); `tsc -b --force` clean.
