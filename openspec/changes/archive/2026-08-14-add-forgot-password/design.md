## Context

Every reusable primitive this feature needs already exists: `randomSecret()` (crypto/rand, 32 bytes, base64-url) and `hashToken()` (SHA-256 hex) in `service/identity.go` already back sessions and API tokens; `SessionRepo.DeleteByUser` (added in `add-update-user`) already revokes every session for an account. What's genuinely new is outbound email — nothing in this codebase sends email today — and the public, unauthenticated surface that email points at.

## Goals / Non-Goals

**Goals:**
- Let a user with a real, active account recover access via a emailed link, without any admin involvement, when the instance has SMTP configured.
- Never leak account existence, deactivation status, or SMTP-configuration status through response timing or content on the public endpoints.
- Zero new third-party dependencies.

**Non-Goals:**
- No email verification / "confirm your email" flow on account creation — out of scope, a separate concern.
- No password-strength meter or UI beyond what `add-update-user`'s Edit dialog already established (reuses `domain.ValidatePassword`, the same 12-character floor).
- No HTML email templates / rich styling — a plain-text email with one link is sufficient and avoids inventing template infrastructure this project doesn't otherwise need.
- No support for multiple concurrent unexpired reset tokens per user being independently valid — requesting a new one is the recovery path if a link is lost, not something this change needs to explicitly manage (see Decisions).

## Decisions

- **`net/smtp` (stdlib), not a third-party mailer library.** The project has zero email infrastructure today; stdlib `net/smtp` with `PlainAuth` over STARTTLS covers the overwhelming majority of real SMTP providers (SES, SendGrid's SMTP relay, self-hosted Postfix, etc.) without adding a dependency. A thin `internal/mailer` package wraps it behind a small interface (`Send(to, subject, body string) error`) so the service layer doesn't import `net/smtp` directly and tests can substitute a fake.
- **Feature-availability flag, not a runtime error.** `passwordResetEnabled` on `GET /api/v1/meta` (mirrors `publicProjectsEnabled`'s existing kill-switch shape) is `true` only when every required `TESTPULSE_SMTP_*` var plus `TESTPULSE_PUBLIC_URL` is set. The login page conditionally renders "Forgot password?" only when true — a self-hosted instance that never configures SMTP simply never shows the link, rather than showing it and failing at submit time.
- **New `password_reset_tokens` table**, not reusing `sessions` or `api_tokens` — different lifecycle (single-use, short 30-minute expiry, exists to prove "I received this email" not "I'm currently logged in"). Shape mirrors `api_tokens`: `token_hash` unique, hashed via the existing `hashToken()`; `used_at` nullable timestamp marks single-use (set on redemption, never deleted — so a reused/expired-link attempt has a real row to reason about, not silently "not found"); `ON DELETE CASCADE` on `user_id`, matching the policy `00014_cascade_user_deletion.sql` already established for sessions/API tokens.
- **`POST /api/v1/auth/forgot-password` always returns `200`, regardless of outcome.** Unknown email, deactivated account, or SMTP not configured — same response, same rough latency shape (the store lookup happens either way; only the email-send step is skipped). Enumeration resistance follows directly from "the response never depends on what's true," not from asking the client to also guess right.
- **A new forgot-password request does not invalidate a prior unexpired token** — simplest correct behavior: multiple valid tokens for the same user can coexist; redeeming any one of them (a) sets its own `used_at` and (b) revokes all sessions via the existing `SessionRepo.DeleteByUser`, which is what actually matters for security (a stale, un-redeemed second link left in an old email is inert once its 30-minute window passes, and can't do anything worse than the first one already could).
- **Rate limiting**: reuse the existing per-IP token-bucket limiter (`server/identity_handlers.go`'s `newLoginRateLimiter`) at the same 5-req/min-burst-5 shape, applied to `/api/v1/auth/forgot-password` — the same abuse surface as login (unauthenticated, triggers real work), same mitigation.
- **Testing without a real SMTP server**: Go service/HTTP tests inject a fake `mailer.Sender` (no network at all — see task 4.1). For E2E, which runs the real compiled binary, `deploy/compose/docker-compose.yml` gains a **Mailpit** service (`axllent/mailpit`, MIT-licensed, single static binary — a fake SMTP server with a REST API for reading what it received) as the `app` service's default SMTP target, permanently, not an E2E-only override. Two things this buys beyond E2E: (1) a developer running the compose stack locally can actually see sent emails at Mailpit's web UI (`:8025`) while manually testing the flow, and (2) the demo/evaluation stack now has `passwordResetEnabled: true` out of the box, so an evaluator sees the whole feature working, not just a hidden link — this changes the Sample-Project-showcase assessment from "not applicable" to "demoable by default." Playwright's E2E test hits Mailpit's REST API (`GET /api/v1/messages`) to fetch the sent email and extract the reset link, exercising the real `net/smtp` code path end-to-end rather than a stub. The real `testpulse.fly.dev` deployment is unaffected — it uses `fly.toml`, not this compose file, and stays with no SMTP configured (or the operator's own choice) unless explicitly set up.

## Risks / Trade-offs

[Stdlib `net/smtp` has no built-in retry/queue — a transient SMTP failure means the email is simply lost] → Acceptable for v1: the user can just submit the form again (rate-limited, not blocked); a queue/retry system is real infrastructure this project doesn't have a reason to build yet for a single transactional email type.
[Self-hosted operators must correctly configure 6 new env vars for this to work at all] → Matches the project's existing configuration philosophy (fail-fast-by-name, `TESTPULSE_ADMIN_EMAIL`/`_PASSWORD` already optional-but-paired) — `passwordResetEnabled` reporting `false` when partially configured (rather than a confusing runtime error) is the actual mitigation, not a smoother setup wizard.
[A locked-out user on an instance with no SMTP configured has no self-service path at all] → Explicitly accepted (see proposal's "Why") — they contact their Tenant Admin, who has a real reset path since `add-update-user` shipped. This is strictly better than today (no path existed for anyone before that shipped either).
