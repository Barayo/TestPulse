## 13. Fully custom, instance-wide roles (design.md D10 — scope added mid-implementation)

User asked "where can the admin create/customise roles?" — role customization had been an explicit Non-Goal for v1 (fixed Tester/Contributor/Project Admin, hardcoded permissions). Clarified via AskUserQuestion: build customization now (not deferred), fully custom roles (not just editable capabilities on the three fixed names), instance-wide scope (not per-project). This is a real architectural pivot, not an additive feature: once role identity isn't fixed at compile time, the original ordinal ranking (`tester < contributor < project_admin`, enforced via `AtLeast(min)`) has no fixed reference role left to rank against. ## 14. Visual review fix — pages must not render as an empty, interactive project when the project/run is inaccessible

User caught this navigating to a suites URL for a project no longer in the (post-rebuild) database: the page showed a fully-functional "New suite" form and "No suites yet." instead of any error, with the header itself showing "Select project" (i.e., the app knew the project wasn't real, but the page didn't). Root cause: five pages (`ProjectPage`, `SuitesPage`, `RunsPage`, `FolderExplorerPage`, `RunPage`) fetch their project (or run) via `openapi-fetch`, which resolves `{data: undefined, error}` on a non-2xx rather than throwing — none of the five checked for that case, so a 404 *or* a 403 (a user with no access to the project — same shape as "does not exist" over the wire, deliberately, per D6) rendered as a blank-but-fully-interactive empty project rather than any error state. User's framing: "the profile should not even see the option of creating when the action is not allowed... it should not see a project where it has no access" — this is a frontend gap, not a backend one; the backend already correctly blocks the underlying write.
