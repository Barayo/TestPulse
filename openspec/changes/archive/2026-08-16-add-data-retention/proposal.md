## Why

Runs and archived projects accumulate indefinitely today — there is no way to permanently remove a run once created, or an archived project once nobody needs it, even though both are pure maintenance overhead once they'll never be needed again. This is about reclaiming storage/performance headroom, not privacy or compliance: nothing here is about erasing a person's data, only removing test-execution history and shut-down projects an admin has explicitly confirmed are safe to discard.

## What Changes

- **BREAKING**: none — this only adds new destructive capabilities that don't exist today; nothing existing changes behavior.
- New: `DELETE /api/v1/runs/{runId}` — permanently deletes a run and everything scoped to it (run items, results). Gated by a new `runDelete` permission flag (project-scoped, same D11 per-resource-flag model `add-project-rbac` established), not bundled into the existing `runCreate`/`runRecordResult` flags.
- New: permanent deletion of an already-archived project — removes the project and everything inside it (sections, cases, case versions, suites, runs, run items, results, membership rows). Only available once a project is archived (`projects.archived = true`); an active project cannot be deleted this way. Triggered by a Project Admin on their own project, gated by a new `projectDelete` permission flag — kept separate from the existing `manageProject` flag (which covers rename/describe/archive) rather than folded into it, consistent with D11's "concrete per-resource actions, not broad ones" principle: a role that can rename or archive a project shouldn't automatically be able to permanently destroy it. Deletion authority follows whoever administers the project day-to-day, deliberately asymmetric with project *creation* staying Tenant-Admin-only: creation is a resource-provisioning decision, cleaning up a project you already administer is not. Because a project can hold an unbounded amount of run history, the actual purge runs asynchronously in the background (an in-process worker, not a new deployable — design.md D6): the confirming request returns immediately, the project disappears from lists right away, and everything scoped to it is permanently removed over the following seconds-to-minutes without further action.
- Every *manual* deletion (run or project) is explicitly confirmed by the actor triggering it (reusing the confirmation-dialog pattern `add-project-rbac` design.md D12 established for "Reset to defaults"), naming exactly what's being deleted before it happens.
- **Scope revised 2026-08-15**: the change's original driving motivation — a customizable automatic cleanup policy for very old runs — was dropped from the initial design and only manual, one-at-a-time deletion shipped. Restored: a single, instance-wide, Tenant-Admin-configurable run-retention threshold (`GET`/`PATCH /api/v1/instance-settings`, alongside the existing `publicProjectsEnabled` switch). Deliberately narrow: **runs only** (not projects — project deletion keeps its manual archive-then-delete two-step, D4, since a whole project is a much larger, more consequential thing to auto-destroy than one closed run), **closed runs only** (an open run is still actively being worked; auto-deleting it out from under someone would be actively dangerous, not just surprising), and **age measured from the run's own `created_at`** (no separate "last activity" signal exists to hook into, and re-deriving one is out of scope). A background worker (`RunRetentionWorker`, separate from the existing `ProjectDeletionWorker` — different trigger, different cadence, not the same mechanism) periodically sweeps for eligible runs and deletes them the same way a manual `DeleteRun` call would. `0` (the default) means the policy is off; nothing is auto-deleted until a Tenant Admin sets a real threshold.
- Automated deletions still need an audit trail — nobody triggered them by hand, so `domain.ActorKind` gains a third value, `system`, purely for this: the append-only audit log's own design principle ("record for every mutating operation... capturing the acting actor") shouldn't have a silent exception just because the actor wasn't a person or a token this time.
- New, in-scope prerequisite found while designing the delete-project UI (Pepe review, 2026-08-15): archiving a project has no reverse today — `Service.UpdateProject` only ever acts when `archived: true` is sent; `archived: false` silently no-ops. The archive-then-delete flow this change relies on (D4) implicitly assumes archiving is a reversible, low-stakes first step, so this change also adds a real `Unarchive` capability (mirrors `Archive` exactly — same permission, same shape) rather than shipping a Switch that quietly does nothing when flipped back off.
- Also found while designing: `GET /api/v1/projects/summaries` excludes archived projects (`WHERE NOT archived`) — but the delete-project confirmation dialog needs exactly those counts for an archived project (D5). This filter is dropped as part of this change; nothing today depends on excluding archived projects from summaries, and leaving it in place would silently show 0/0 counts in the one dialog that most needs them right, plus corrupt `ProjectsPage.tsx`'s existing summary merge the moment archived projects become visible via the new badge.
- No user deletion or deactivation changes — out of scope for this change (deactivation already exists via `add-identity-basics`/`add-project-rbac`; permanent user removal was raised while scoping this change but the user narrowed the target to runs and deactivated projects only).
- No deletion of individual cases, sections, or suites beyond what already exists (`caseDelete`/`sectionDelete` from `add-project-rbac` D11 already cover those) — this change is specifically about runs (no delete capability exists for them today) and whole archived projects (also no delete capability today, only archive).
- **Scope revised 2026-08-16**: restored automatic *project archiving* too — a single, instance-wide, Tenant-Admin-configurable inactivity threshold (`autoArchiveInactiveDays` on the same `GET`/`PATCH /api/v1/instance-settings` endpoint, `0` default = off) that automatically archives a project once it's gone quiet for that many days. Deliberately **archive, not delete** — archiving is already reversible and low-stakes (D7); nothing about this reverses that. "Inactive" is computed at sweep time (not a maintained column) as the newest of the project's own `createdAt`, its most recent run's `createdAt`, its most recent case-version's `createdAt`, and its most recent suite's `createdAt` — a real activity signal, unlike D8's run retention which deliberately stuck to raw `createdAt` alone. A Tenant Admin can exempt an individual project from this policy (`autoArchiveExempt` on the project) — a one-way, Tenant-Admin-granted exemption, **not** a Project-Admin-facing self-service override: Pepe's design review (2026-08-16) found this codebase's one existing instance/project two-tier setting (`publicProjectsEnabled`/`publicAccess`) is a one-directional AND-gate where the instance flag can only *restrict*, never grant, and rejected a literal "project overrides the instance default" shape as introducing a new, unprecedented trust relationship (a Project Admin unilaterally defeating a Tenant Admin's org-wide policy). A third background worker (`ProjectAutoArchiveWorker`) sweeps and archives eligible projects the same way a manual archive does, audited under the same `system` actor kind D8 introduced.

## Capabilities

### New Capabilities
(none — both additions are new requirements on existing capabilities, not new domains)

### Modified Capabilities
- `test-execution`: adds a "Deleting a run" requirement — permanent, confirmed, cascades to the run's items and results, gated by a new `runDelete` permission; adds an "Automatic run retention" requirement — a Tenant-Admin-configurable, instance-wide age threshold for closed runs, off by default.
- `test-authoring`: adds a requirement to the existing "Project management" section for permanently deleting an already-archived project, cascading to everything scoped to it; adds an "Automatic project archiving" requirement — a Tenant-Admin-configurable, instance-wide inactivity threshold, off by default, with a Tenant-Admin-only per-project exemption.
- `authorization`: adds `runDelete` and `projectDelete` to the permission-flag catalog `add-project-rbac` design.md D11 established (ten flags → twelve), and documents the project-deletion authorization rule. **No new flag for the auto-archive exemption** — deliberately Tenant-Admin-only regardless of custom roles (design.md D9), the same asymmetry project *creation* and *membership assignment* already have with project administration.
- `audit-log`: adds `system` as a third `actorKind`, alongside `user`/`agent`, for audit entries recorded by automated background processes rather than a resolved request-time Actor.

## Impact

- **Schema**: no new tables; a new nullable `projects.deleting_at` column marks a project as queued for background deletion (design.md D6); deletion cascades through existing/amended FK relationships (sections/cases/suites/runs/items/results reference `projects`/`runs`, gaining `ON DELETE CASCADE` where it doesn't already exist — confirmed in design.md D2, seven FKs total). `instance_settings` gains `run_retention_days integer DEFAULT 0 NOT NULL` and `auto_archive_inactive_days integer DEFAULT 0 NOT NULL` (both 0 = off). `projects` gains `auto_archive_exempt boolean DEFAULT false NOT NULL`. `audit_log`'s `actor_kind` CHECK constraint gains `system` as a third allowed value.
- **API**: new `DELETE /api/v1/runs/{runKey}` (synchronous, 204); new `DELETE /api/v1/projects/{projectKey}` (asynchronous, 202 Accepted — the project is marked for deletion and hidden immediately, actually purged by a background worker); new `GET /api/v1/instance-settings` (Tenant-Admin-only — nothing previously needed to *read* the settings row outside `/meta`'s narrow public subset); `PATCH /api/v1/instance-settings` gains `runRetentionDays` and `autoArchiveInactiveDays`; `PATCH /api/v1/projects/{projectKey}` gains `autoArchiveExempt` (accepted only from a Tenant Admin — checked in `Service.UpdateProject`, since the route's own permission gate, `manageProject`, is coarser than this specific field needs).
- **Domain/service/store**: two new permission flags (`runDelete`, `projectDelete`) alongside the ten from D11 (mirrors that pattern exactly — migration columns, `domain.Permission` consts, `Role`/`Permissions` struct fields, `EffectivePermissions` query, route enforcement); a new service method for run deletion (synchronous); for project deletion, a service method that marks the project for deletion (after checking the archived precondition server-side, not just hidden in the UI) plus a new in-process background worker that performs the actual chunked, resumable purge; a second, independent in-process background worker (`RunRetentionWorker`) that periodically sweeps closed runs past the configured age threshold and deletes them the same way `DeleteRun` does; a third, independent worker (`ProjectAutoArchiveWorker`) that periodically sweeps non-archived, non-exempt projects for inactivity and archives eligible ones the same way a manual archive does; `domain.ActorKind` gains `system`.
- **UI**: a destructive "Delete" action on a run's page (and/or the runs list) and on an archived project's card/page, each behind a confirmation dialog naming the target and what it cascades to, matching `RolesPage.tsx`'s "Reset to defaults" dialog pattern; `InstanceSettingsPage.tsx` gains "Run retention" and "Auto-archive inactive projects" controls (both Tenant-Admin-only, alongside the existing "Public project access" switch) — a shared pill-selector component (Pepe design review, 2026-08-15/16) since both are the same 5-segment Off/30d/90d/365d/Custom shape, differing only in copy and (for Run retention alone) the armed-state destructive callout, since auto-archive is reversible and stays a plain muted line; `ProjectSettingsPage.tsx`'s existing "Archive project" card gains a conditional exemption line/toggle, visible to any project member but only editable by a Tenant Admin.
- **Audit log**: manual deletions/archives are audited writes as the requesting actor (`s.audit(ctx, "delete"/"archive", "run"/"project", id)`); automatic ones (run retention, project auto-archive) are audited under the same `system` actor kind, distinguished from manual ones purely by `actorKind`, not a different action string — the append-only audit log itself is unaffected by what gets deleted/archived (it doesn't reference run/project rows by FK, only records ids/types as text).
