## Context

`add-testrail-importer` (archived) built the first vendor content importer and deliberately made almost everything about it source-opaque: the `import_jobs` table, `apps/api`'s create/poll/claim/patch routes, the poll-not-push control direction, encrypted-credentials handling, the scoped-agent-token claim model, and the browser's data-driven entry-point menu all treat `source` as an arbitrary string. `add-qase-importer` (archived) proved that reusability by adding a second source with zero `apps/api` changes. This change adds a third: Zephyr Scale (#191, split from an original combined Zephyr Scale/Xray card once investigation showed Xray's native-Jira-issue model is architecturally distinct enough to need its own design — tracked separately as #196). Everything not called out as a new decision here is inherited from `add-testrail-importer`'s and `add-qase-importer`'s design.md verbatim.

Zephyr Scale Cloud's REST API v2 (base URL `https://api.zephyrscale.smartbear.com/v2`) was verified two ways: its generated OpenAPI type contracts, sourced from the published `bun913/zephyr-api-client` npm package's generated `data-contracts.ts` (itself produced by `swagger-typescript-api` from Zephyr's own spec — inspected directly via `gh api repos/bun913/zephyr-api-client/contents/...`), for `TestCase`, `Folder`, `TestStep`, and `TestScript` shapes; and general web search for auth/base-URL confirmation. **One area could not be verified this way**: the exact custom-field-type enum (the client package inspected has no `customfields` resource file, and no authoritative source turned up a confirmed type list) — called out explicitly in D-Z5 as an open question rather than asserted with false confidence.

## Goals / Non-Goals

**Goals:**
- Import a Zephyr Scale Cloud project's `TEST_CASE`-type folder tree and cases (with steps and mappable custom fields) into a TestPulse project, through the exact same Connect → Preview → Result flow and dry-run guarantee `add-testrail-importer`/`add-qase-importer` shipped.
- Add `zephyr-scale` as a third, fully-plugged-in `source` without touching `apps/api`'s schema, routes, or handlers.

**Non-Goals:**
- Run/result history import — inherits the same deferral as TestRail/Qase, for the same reason (`CaseVersion` rows have no bulk-backfill path).
- Reconstructing Zephyr Scale's own case edit/version history as TestPulse case versions — an imported case starts at version 1 (its current state), matching TestRail/Qase's behavior.
- Zephyr Scale Server/Data Center — this change targets Cloud only. Server/DC exposes a structurally different, self-hosted REST API (coupled to the customer's own Jira instance URL, closer in shape to TestRail's always-required site URL) that hasn't been investigated; a Cloud-only v1 mirrors Qase's own "no self-hosted product" simplification, but for Zephyr Scale this is a deliberate scope cut, not an absence of a Server/DC product — flagged honestly as a real gap, not an oversight.
- "Call to test" steps (a Zephyr Scale step that delegates execution to another test case by key, with its own parameter bindings) — `domain.Step` has no delegate-step concept at all (not Zephyr-specific), matching how Qase's nested child-steps and data-driven parameters are silently out of v1 scope rather than reported per case.
- Xray — tracked separately as #196, per the split above.

## Decisions

**Inherited unchanged from `add-testrail-importer`/`add-qase-importer` (D1-D5, D9 in TestRail's design; D-Q5's package-layout pattern):**
- Control direction: the importer polls `apps/api`; `apps/api` never calls the importer.
- `apps/api` owns the generic `import_jobs` table; `source: "zephyr-scale"` is just another opaque value in the existing `source text` column — no migration.
- The same `POST/GET .../import-jobs[/{jobId}]` (browser-facing) and `GET/PATCH /import-jobs` (agent-facing) routes, unchanged, no new `packages/shared/openapi.yaml` surface.
- Per-project-scoped agent token model (one importer deployment per target project).
- Attribution: the job's `created_by` records the authorizing human; imported content is attributed to the importer's own agent identity.
- Progress UI: count-up against `progress_current`/`progress_total`, tight poll interval.

**D-Z1: Auth, base URL, and project addressing — single Bearer token, fixed Cloud endpoint, string `projectKey`; no site URL field.**
Verified via the generated client contracts and corroborating community documentation: authentication is a single API access token (generated from a user's Jira profile → Zephyr Scale API Access Tokens page), sent as a Bearer token against the fixed, vendor-hosted `https://api.zephyrscale.smartbear.com/v2` — unlike TestRail's own-instance site URL, the Cloud API endpoint never varies per customer, so there's no site-URL field on the Connect screen (matching Qase's D-Q2 simplification, though for a different underlying reason — Qase has no self-hosted product at all, while Zephyr Scale Cloud specifically has one fixed endpoint even though a separate self-hosted product exists). Every resource is addressed by `projectKey` (the Jira project's own key, e.g. `PROJ`) as a query/path parameter — confirmed on `Folder`/`FolderInput` (`project: ProjectLink` resolved from `projectKey` at creation) — the same "the user already knows this string from their own vendor UI" shape as Qase's `code` (D-Q1), not a numeric id requiring a separate lookup call like TestRail's. Credentials map: `apiToken`, `projectKey`.

**D-Z2: Domain mapping — `TEST_CASE`-type folders form a direct `parentId` tree, same shape as Qase's D-Q3.**
`GET /folders?projectKey=...&folderType=TEST_CASE` (confirmed: `Folder{id, parentId, name, index, folderType, project}`, `FolderType` is one of `"TEST_CASE" | "TEST_PLAN" | "TEST_CYCLE"` — the same flat resource carries all three folder kinds, filtered by `folderType`) returns one tree per project via `parentId`, with no intermediate "suite" concept to split out (unlike TestRail's D6). Mapping:
- A `TEST_CASE`-folder with `parentId: null` → a top-level TestPulse Folder.
- A `TEST_CASE`-folder with a non-null `parentId` → a nested Folder beneath its parent's mapped Folder, recursively.
- A case (`TestCase.folder`, a nullable Link resolved to the matching fetched folder) → a TestPulse Case in its mapped Folder, or the project's root folder if `folder` is null.
`TEST_PLAN`/`TEST_CYCLE` folders are never fetched — this importer only ever queries `folderType=TEST_CASE`.

**D-Z3: Step mapping — step-by-step steps map directly; a script-only case's narrative/BDD text is preserved in Description, not silently dropped.**
Two independent, mutually-exclusive representations exist per case (confirmed via the generated contracts): `GET /testcases/{key}/teststeps` (a `TestStep` list, each either `inline: {description, testData, expectedResult, customFields}` or `testCase: {testCaseKey, parameters}` — a delegate "call to test" step) and `GET /testcases/{key}/testscript` (`{type: "plain" | "bdd", text}` — a single freeform or Gherkin-scenario text blob, *not* a step list). A Zephyr Scale case uses one or the other, not both, depending on how it was authored.
- If `teststeps` returns any `inline` entries: each maps to `domain.Step{Action, Expected}` — `Action` is `description`, with `testData` appended on its own line (`"<description>\n\nTest data: <testData>"`) when present, since `domain.Step` has no separate test-data field (confirmed: only `Action`/`Expected`/`GroupRef` exist) and losing it silently would violate this project's established "never silently discard vendor content" posture (TestRail D7, Qase D-Q4). `testCase`-delegate entries are skipped per the Non-Goals section above.
- Else, if `testscript` exists (`type: "plain"` or `"bdd"`): its `text` is appended to the case's `Description` field, prefixed to identify its origin (e.g. `"Zephyr Scale BDD script:\n\n<text>"` or `"Zephyr Scale test script:\n\n<text>"` for plain text) — preserved as readable prose rather than force-fit into fake steps or dropped. The case's `Steps` list is empty in this case.
- Else (neither present): the case imports with no steps, matching TestRail/Qase's own handling of a case with no defined procedure.

**D-Z4: Native priority and status are not mapped — matches the established TestRail/Qase precedent.**
Confirmed by reading `tools/import-connector/internal/importer/importer.go`: neither the TestRail nor Qase importer maps the vendor's own native priority or status onto TestPulse's `Priority` enum or any other native `CaseContent` field — every imported case receives `CaseContent.Validate()`'s default. This change follows the same precedent rather than introducing new mapping scope: Zephyr Scale's `TestCase.priority`/`TestCase.status` (both Links) are simply never resolved or used at all — `internal/zephyrscaleclient` doesn't even fetch `GET /priorities`/`GET /statuses` (there is nothing to resolve them *to*, so doing so would be dead code), and no mapped case carries either value.

**D-Z5: Custom field mapping — value-shape-based, more conservative than TestRail/Qase (no `select` support in v1), resolved after exhausting live-verification options.**
`TestCase.customFields` is confirmed as `Record<string, any>` (flat, name-keyed — unlike Qase's numeric-id-keyed array) — a case's custom field values arrive as a plain name→value map with no id. The definitions endpoint that would describe each field's *type* and (for choice-type fields) its configured options is not part of the documented public v2 surface as far as this design could establish: no Zephyr Scale Cloud trial account was available during this design/implementation pass, SmartBear's own `api-docs` URLs return 404, and `bun913/zephyr-api-client`'s generated `data-contracts.ts` (produced by `swagger-typescript-api` from the real published spec) has no `CustomFieldDefinition`/type-enum type at all — only the opaque `customFields: Record<string, any>` value map. Rather than guess a type-enum that could silently misclassify a field, this change maps by the JSON **value shape** actually present on each case instead of a vendor-defined type: a string value → TestPulse `text` (created/reused per import); any other JSON shape (object, array, number, boolean, null) → dropped and named individually in the job's report, exactly like an unmappable TestRail/Qase field type. No Zephyr Scale custom field maps to TestPulse `select` in this change — deliberately narrower than TestRail's/Qase's own custom-field mapping (D7/D-Q4), since distinguishing a genuine single-choice field from free text requires the type metadata this API surface doesn't expose here. A real, stated v1 limitation, not an oversight — see Risks and `docs/integrations.md`.

**D-Z6: `tools/import-connector` package layout — `internal/zephyrscaleclient` alongside `internal/testrailclient`/`internal/qaseclient`, sharing `internal/testpulseclient` and the poller/config skeleton unchanged.**
Mirrors D-Q5 exactly: a new hand-rolled REST client (`internal/zephyrscaleclient`, no SDK dependency), and `internal/importer` gains a `zephyr-scale` branch (selected by the claimed job's `source`) implementing D-Z2/D-Z3/D-Z4/D-Z5. `internal/config`, `internal/poller`, `internal/testpulseclient`, and `cmd/import-connector/main.go` are unchanged.

**D-Z7: Trademark — same conservative pattern as D10/D-Q6, applied by default; SmartBear's own policy not yet independently verified.**
No published SmartBear trademark/brand-usage policy for Zephyr Scale was found during this design pass (same situation as Qase's D-Q6, different from TestRail's explicit Idera policy). Applies the identical conservative pattern: generic tool name (`tools/import-connector`, `--source=zephyr-scale`), "Import from Zephyr Scale" as plain referential UI copy, no Zephyr/SmartBear logo, `docs/integrations.md` and the Connect screen carry the same disclaimer-footnote treatment. Tracked under the same standing concern issue (#195) as TestRail, Qase, and the remaining vendor cards.

**D-Z8: In-app entry point — one more array entry, no new UI primitive.**
Matches D8/D-Q7: "Import from Zephyr Scale" is a third entry in the same data-driven source list (menu → `/projects/import/zephyr-scale`, the existing `/projects/import/:source` route, unchanged). The Connect screen's credential fields are rendered per-source: API access token + project key (no site URL, no base-URL override — D-Z1's fixed endpoint needs neither).

## Risks / Trade-offs

- **[Risk] D-Z5's custom field mapping supports only `text`, not `select`, unlike TestRail/Qase.** → Mitigation: accepted as a stated v1 limitation rather than a guessed `select` mapping that could misclassify a field with no way to verify the guess (the type-metadata endpoint isn't part of the documented public API surface this design could establish access to). A future change can add `select` support once either a Zephyr Scale Cloud account becomes available to verify against, or SmartBear documents the relevant endpoint.
- **[Risk] Cloud-only scope (Non-Goals) means a customer on Zephyr Scale Server/DC gets no importer at all.** → Accepted for v1: Server/DC's API is structurally different enough (self-hosted, coupled to the customer's own Jira URL) that supporting it is a materially separate design, not a follow-up tweak — revisit only if real demand surfaces, matching this project's "no speculative scope" standing practice.
- **[Trade-off] A script-only case's procedure lands in `Description` as prefixed prose, not structured steps (D-Z3).** → Accepted: better than silent loss, and a case authored as freeform/BDD text in Zephyr Scale was never going to map cleanly onto TestPulse's discrete `Action`/`Expected` step shape regardless of effort spent — the alternative (synthesizing fake steps by splitting on newlines) would misrepresent the source content more, not less.
- **[Trade-off] `testData` is appended into `Action`'s text rather than getting its own field (D-Z3).** → Accepted: `domain.Step` has exactly two fields by design; inventing a third for one vendor's one field would be scope creep beyond this change, and appending preserves the information losslessly for a human reader even if it's not a separate structured field.

## Migration Plan

Additive only, matching Qase's own narrower-than-TestRail shape: no new migration, no new `apps/api` routes, no `packages/shared/openapi.yaml` changes. Everything new lives in `tools/import-connector` and the frontend's existing data-driven source list.

Suggested build sequencing:
1. **Live-verification attempt for D-Z5's custom-field type enum** — exhausted before any custom-field mapping code is written; resolved to the value-shape-based `text`-only approach documented in D-Z5 once no live account or authoritative spec was reachable.
2. `tools/import-connector/internal/zephyrscaleclient` — REST client (folders, test cases, test steps, test scripts, priorities, statuses, custom fields), TDD per the existing `testrailclient`/`qaseclient` test pattern.
3. `tools/import-connector/internal/importer` — add the `zephyr-scale` mapping branch (D-Z2/D-Z3/D-Z4/D-Z5), reusing the existing dry-run/fake-writer test harness.
4. `apps/web`: `ProjectsPage.tsx` source-list entry, `ImportProjectPage.tsx` Zephyr Scale Connect-screen fields (API token + project key only).
5. `e2e/import-connector.spec.ts` (or a new sibling spec) — scenarios for the parts reachable without a live Zephyr Scale account (menu entry, route navigation, Connect form validation), matching TestRail/Qase's own E2E scope limitation.
6. `docs/integrations.md` — extend with the Zephyr Scale section and disclaimer; `deploy/compose/docker-compose.yml` and the Helm chart's `import-connector` templates gain a Zephyr Scale-flavored example alongside the existing TestRail/Qase ones.
