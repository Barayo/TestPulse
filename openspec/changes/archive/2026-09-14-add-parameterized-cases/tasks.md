## 13. Post-implementation review round (Luis/Jose/code-reviewer/ux-reviewer/Paco/Pepe, per standing practice)

Full parallel review dispatched against the diff above. Verdict: no security vulnerabilities (Luis, incl. live DAST — XSS/SQLi/IDOR/template-injection all actively tried and ruled out), architecture sound (Jose: "proceed"). Real, confirmed issues found and fixed:

- **[Critical, code-reviewer]** Renaming a column to an already-existing name (or to "Name") silently merged/clobbered row data, both client- and server-side unguarded. Fixed: `CaseParametersEditor.tsx`'s `renameColumn` now blocks with an inline message; `domain.go`'s `validateParameters` rejects duplicate column names server-side as defense in depth. Tests: 2 new `CaseParametersEditor.test.tsx` cases, 1 new `TestCaseContentParametersValidation` sub-case.
- **[Critical, code-reviewer]** The column-rename `<th>` was keyed by the mutable column name itself, so every keystroke unmounted/remounted the input and dropped focus (only the first character of a rename ever committed). Fixed: keyed by index instead (also applied to the sibling data-cell `<td>`s for consistency). Regression test: a controlled-harness test typing 3 characters in one continuous `userEvent.type` call, which reproduced the bug exactly (`usernamex` instead of `usernamexyz`) before the fix.
- **[High, Paco — live QA]** `CaseDetailPage.tsx`'s `saveEdit` and `CreateCasePage.tsx`'s `submitCreate` never checked `response.ok` — a server-side validation rejection (e.g. unmatched placeholder) silently reverted the edit to the original content / did nothing on create, with zero error shown. This was the one thing that defeated the feature's core safety guarantee from the user's seat. Fixed: both now surface `(error as {error?:string})?.error` inline near the save/create button and stay in edit mode / keep the typed input. Tests: 1 new case each in `CaseDetailPage.test.tsx` and `CreateCasePage.test.tsx`; also fixed 2 pre-existing `CaseDetailPage.test.tsx` tests that had been silently relying on `mockPUT`'s default `undefined` resolution (unhandled-rejection warnings once the code started destructuring the response).
- **[Medium, Pepe]** `RunItemDetailPage.tsx`'s "Test data" chips rendered via `Object.entries(item.testDataRow)` — alphabetical (Go map JSON marshaling), disagreeing with the author's defined column order shown on the case's own Test Data table. Fixed by ordering chips via `item.content.parameters?.columns` (already present on the RunItem per D9's "whole table rides along" quirk — turned into the fix rather than a separate contract change), falling back to `Object.keys` if absent. Regression test in `RunItemDetailPage.test.tsx`; confirmed live post-rebuild (chips now read username → password → expectedResult, matching the seeded case's column order).
- **[Low-medium, Jose + Luis independently]** `service.AddRunItem`'s parameterized-case expansion looped the single-item `store.AddItemSpec`, each its own transaction — a partial failure (e.g. re-adding a case whose rows partly already exist) could leave some rows committed and others not, unlike `CreateRun`'s single-transaction atomicity. Fixed: new `store.RunRepo.AddItemSpecs` pins every spec in one transaction; `AddItemSpec` is now a one-line wrapper; `AddRunItem` calls it once. Regression test `TestAddItemSpecsIsAtomicAcrossRows` (pre-seed a colliding row, batch-add two more including the collision, confirm zero of the batch committed).
