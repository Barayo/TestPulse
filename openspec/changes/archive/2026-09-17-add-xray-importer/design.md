## Context

`add-testrail-importer` (archived) established the source-opaque `import_jobs` machinery; `add-qase-importer`, `add-zephyr-scale-importer`, and `add-kiwi-tcms-importer` each proved it reusable against increasingly different vendor shapes — REST+JSON (Qase, Zephyr Scale) and hand-rolled XML-RPC (Kiwi TCMS). This change (Xray, #196, split from #191) is the first to need **two genuinely different clients for one source**: Xray Cloud (client_id/secret → JWT, GraphQL) and Xray Server/Data Center (Jira's own PAT auth, REST), because the user explicitly chose to ship both in v1 rather than the Cloud-only default every prior importer in this family used.

Two research passes against Xray's own published documentation (`docs.getxray.app`, `getxray.app`) grounded every factual claim below; both are cited inline. Confirmed facts this design relies on: Tests/Preconditions/Test Sets/Test Plans/Test Executions are native Jira issue types, not an Xray-only data store; there's an explicit "Test Repository" folder tree per project, separate from Jira's project/component/label structure; manual test steps are structured (`action`/`data`/`result`), not freeform, for the "Manual" test type specifically — Cucumber/Generic test types carry a freeform script/scenario instead; Cloud's GraphQL `getTests`/`getTest` can pull both Xray-native fields and named Jira fields (via a `jira(fields: [...])` argument) in one query, while Server/DC genuinely splits the two: Jira's own REST API for issue fields (summary/description), Xray's `raven` REST API for steps and repository structure.

## Goals / Non-Goals

**Goals:**
- Import an Xray project's Test Repository folder tree and its Manual/Cucumber/Generic Test issues (with structured steps where Xray has them) into a TestPulse project, through the same Connect → Preview → Result flow and dry-run guarantee every prior importer shipped.
- Support both Xray Cloud and Xray Server/Data Center as one v1, since they're the two deployment modes real Xray customers actually run — not deferring Server/DC to a follow-up card, per explicit user direction overriding this family's usual Cloud-only-first default.
- Add `xray` as a fifth, fully-plugged-in `source` without touching `apps/api`'s schema, routes, or handlers.

**Non-Goals:**
- Test Execution/run-result history import — inherits the same deferral as every prior importer (no bulk `CaseVersion`/run-result backfill path).
- Test Sets, Test Plans (Xray's, distinct from TestPulse's `Plan`/run concept), and Preconditions — native Jira issue types with no matching TestPulse concept to import into; only the Test Repository folder tree and the Test issues within it are imported, mirroring how Kiwi TCMS's D-K3 scoped to structural case data only.
- Reconstructing a Test issue's Jira edit history as TestPulse case versions — an imported case starts at version 1, same as every prior importer.
- A general-purpose Jira/Xray SDK — this change builds exactly the GraphQL query and REST calls it needs, not a reusable Jira API client.
- Basic Auth for Server/DC — see D-X2; only Personal Access Tokens are supported, to avoid ever storing a real user's Jira password.
- Mid-job Cloud token refresh — see D-X9.

## Decisions

**Inherited unchanged from the prior four importers:**
- Control direction: the importer polls `apps/api`; `apps/api` never calls the importer.
- `apps/api` owns the generic `import_jobs` table; `source: "xray"` is just another opaque value in the existing `source text` column — no migration.
- The same `POST/GET .../import-jobs[/{jobId}]` (browser-facing) and `GET/PATCH /import-jobs` (agent-facing) routes, unchanged, no new `packages/shared/openapi.yaml` surface.
- Per-project-scoped agent token model (one importer deployment per target project).
- Attribution: the job's `created_by` records the authorizing human; imported content is attributed to the importer's own agent identity.
- Progress UI: count-up against `progress_current`/`progress_total`, tight poll interval.

**D-X1: One `xrayclient` package, one `importer.XrayReader` interface, two constructors — not two separate client packages.**
Unlike switching transport (REST vs XML-RPC, Kiwi TCMS's D-K1), Cloud and Server/DC differ in auth and per-call wire format but serve the same logical data (a project's Test Repository folder tree, its tests, their steps). A single `xrayclient.Client` interface with `NewCloud(ctx, baseHost, clientID, clientSecret, projectKey string) (Client, error)` and `NewServer(ctx, siteURL, personalAccessToken, projectKey string) (Client, error)` constructors — each returning a distinct internal struct (`cloudClient` using GraphQL, `serverClient` using REST) satisfying the same `Client` interface (`ListFolders`, `ListTests`, `GetTestSteps`) — keeps `internal/importer`'s mapping logic (D-X4/D-X5/D-X6) mode-agnostic: it only ever calls the shared interface, never branches on Cloud-vs-Server itself. This mirrors how `internal/importer` already doesn't care whether `testpulseclient` calls are REST or something else — the same "consumer only sees the interface" principle, just applied within one vendor for the first time.
*(Rejected)* Two separate packages (`xraycloudclient`, `xrayserverclient`) — considered, but would force `internal/importer` and `internal/poller` to branch on mode explicitly wherever they construct or call the client, duplicating the mapping logic's call sites for no real benefit since the two clients already return identical data shapes.

**D-X2: Auth — Cloud exchanges client_id/secret for a bearer JWT via Xray's own token endpoint; Server/DC requires a Jira Personal Access Token, not Basic Auth.**
Confirmed: Cloud's `POST https://xray.cloud.getxray.app/api/v2/authenticate` takes `{client_id, client_secret}` and returns a JWT valid 24h (docs.getxray.app, Authentication - REST v2). `NewCloud` calls this once at client construction and carries the JWT as an `Authorization: Bearer` header on every GraphQL call, the same "authenticate once, reuse the client" shape as Kiwi TCMS's `Auth.login` (D-K2), just producing a JWT instead of a session cookie. Server/DC has no Xray-specific token exchange — it rides on Jira's own auth. Of Jira's two options (Basic Auth with a real password, or a Personal Access Token), this design requires a PAT: it's the modern, individually-revocable, non-password credential Jira itself recommends (8.14+), and never asks a user to hand TestPulse their actual Jira login password — a stronger stance than Kiwi TCMS's D-K2 could take, since Kiwi TCMS's API genuinely has no PAT-equivalent. Connect-screen credential fields: Cloud mode → `clientId`, `clientSecret`, `projectId`; Server mode → `siteUrl`, `personalAccessToken`, `projectKey`.

**Addendum, discovered during implementation**: Cloud's `getFolder`/`getTests` GraphQL queries take a `projectId` argument documented as "the project id of the Project" (example value `"10000"`) — the internal numeric Jira project id, not the project key string. Xray Cloud's own bearer token (from D-X2's client_id/secret exchange) authenticates only against Xray's GraphQL API, not Jira's REST API, so there is no verified way to resolve a project key to its numeric id without a second, different credential this design deliberately doesn't collect. Rather than guess at an unverified resolution path, Cloud mode's Connect screen asks for the numeric Jira Project ID directly (labeled "Project ID", with help text pointing to where to find it in Jira's own project settings URL) instead of a project key — the same "plain numeric id, friendlier lookup deferred" precedent TestRail's own Connect screen already established (that design's open question, still unresolved there). Server/DC is unaffected: its REST endpoints are confirmed to take `{projectKey}` directly.

**D-X3: Data fetch — Cloud uses one GraphQL query per page (Xray-native fields plus named Jira fields via `jira(fields: [...])`); Server/DC makes separate Jira REST and Xray `raven` REST calls.**
Confirmed via Xray's own GraphQL schema docs: `getTests`/`getTest` returns Xray-native fields (`testType`, `steps { action, data, result }`) directly, and Jira fields (summary, description) via a `jira(fields: ["summary", "description"])` argument in the *same* query — so Cloud needs exactly one GraphQL round-trip per page of tests, no separate Jira REST call. Server/DC's own docs state plainly that issue fields come from Jira's REST API while structured steps are Xray-specific (`GET /rest/raven/1.0/api/test/{testIssueKey}/step`) — genuinely two calls per test on Server/DC, unavoidable given how that surface is documented. Folder tree: Cloud's `getFolder(projectId, path)`; Server/DC's `GET /rest/raven/1.0/api/testrepository/{projectKey}/folders` (root) and `GET .../folders/{folderId}/tests` (tests within a folder, supports `allDescendants=true` and pagination) — both confirmed against docs.getxray.app's Server/DC-specific pages (not the Cloud docs).

**D-X4: Folder tree mapping — a project's Test Repository folder tree maps directly to a nested Folder tree, the same direct-tree pattern as Qase/Zephyr Scale/Kiwi TCMS.**
Xray's Test Repository is confirmed to be a first-class, per-project folder hierarchy independent of Jira's own project/component/label structure — the cleanest structural match of any importer in this family, needing no TestRail-style suite/section split (D6) or Kiwi TCMS-style multi-plan dedup (D-K4) workaround. Root folder (Cloud: root `path`; Server/DC: folder `id -1`) maps to the TestPulse project's top level; each child folder nests beneath its parent's mapped Folder, recursively.

**D-X5: Step mapping — Manual-type tests map structured `action`/`data`/`result` fields directly to `domain.Step`; Cucumber/Generic-type tests map their freeform script/scenario text to the case's description with no steps.**
This is the first importer in the family with real structured step-level fidelity end to end (TestRail also had structured steps, but through a different custom-field-driven path) — Xray's "Manual" test type genuinely has an ordered array of `{action, data, result}` triples, confirmed via both the Cloud GraphQL schema and Server/DC's Test Steps REST endpoint. Non-Manual test types ("Cucumber" — Gherkin scenario text — and "Generic" — a single freeform definition field) have no structured steps at all; their script/scenario/definition text is appended to the imported case's description and the case's `Steps` list is empty, the same resolution Zephyr Scale's D-Z3 and Kiwi TCMS's D-K5 already established for script-only or step-less source cases.

**Addendum, discovered during implementation**: rather than branch on a `TestType` string field (confirmed present on Cloud via `testType.name`, but no equivalent field was independently verified for Server/DC's REST responses), the mapping decision in both clients is driven by **whether `GetTestSteps` actually returns any steps** — behaviorally equivalent, since Xray's own data model only ever populates steps for Manual tests, and avoids relying on a Server/DC field this design pass couldn't verify. Server/DC's `Definition` fallback is narrower than Cloud's for the same reason as D-X6's Cloud custom-field gap: no verified Server/DC field for a Cucumber/Generic test's Gherkin/freeform script was found, so Server/DC's imported description carries only the Jira issue's own summary/description — a real, disclosed v1 limitation for Server/DC specifically (Cloud is unaffected, since `gherkin`/`unstructured` are confirmed GraphQL fields).

**D-X6: Custom field mapping — Xray-native Test-scoped fields (Test Type, Manual Steps Count, etc.) are dropped as non-portable metadata; arbitrary Jira custom fields on a Test issue use value-shape-based mapping, the same honest fallback Zephyr Scale's D-Z5 used.**
Confirmed: Xray does expose its own custom-field types beyond generic Jira fields (Automated Test Type Select List, Manual Steps, Manual Steps Count, Test Type, and fields scoped to Test Steps/Test Runs — docs.getxray.app "Using custom fields"), but these describe Xray's own execution/automation model, not portable case content — TestPulse has no equivalent concept to receive them, so they're dropped (named in the report, not silently lost, same disclosure standard as every prior importer). For a Test issue's *generic* Jira custom fields, research could not confirm any Xray-documented way to introspect a field's type from the importer's perspective (Jira's own `GET /rest/api/3/field` metadata endpoint is a Jira-platform capability, not something Xray's docs address for this use case) — rather than guess at a mapping table, this design applies the exact same fallback Zephyr Scale's D-Z5 already established for an unverifiable vendor type system: map by the field's runtime value shape (a string value → `text` custom field; anything else → dropped, named in the report), documented as a real, stated v1 limitation, not a silent guess.

**Addendum, discovered during implementation**: this value-shape fallback is only reachable for Server/DC. Cloud's GraphQL `jira(fields: [...])` argument requires each Jira field to be named explicitly in the query (confirmed in research), and no Xray Cloud field-discovery query was found to enumerate a project's actual custom field ids ahead of time — Cloud mode's own bearer token also has no access to Jira's own field-metadata REST API (D-X2: it authenticates only against Xray's GraphQL, not Jira's REST API). Rather than hardcode a guessed list of field names that would silently miss every real customer's actual custom fields, **Cloud mode does not import Jira custom fields in v1** — only `summary`/`description` are requested via `jira(fields: [...])`. This is a real, stated Cloud-only limitation, disclosed in `docs/integrations.md`, not a silent gap; Server/DC is unaffected, since its Jira PAT has full REST access to read a Test issue's actual custom field values.

**D-X7: `tools/import-connector` package layout — `internal/xrayclient` alongside the four existing clients, sharing `internal/testpulseclient` and the poller/config skeleton unchanged except for a `mode` field.**
Mirrors the established layout: a new client package (`internal/xrayclient`, exporting the `Client` interface and both constructors from D-X1), and `internal/importer` gains an `xray` branch (`BuildXrayPlan`, `RunXray`) implementing D-X4/D-X5/D-X6. The claimed job's credentials carry a `mode` field (`"cloud"` or `"server"`) that `internal/poller` uses to pick which constructor to call — the only new branching point in the whole pipeline; everything downstream of client construction is mode-agnostic per D-X1.

**D-X8: Trademark — same conservative pattern as the other four; Xray's own policy not yet independently verified.**
No published Xray trademark/brand-usage policy was found during either research pass (same situation as Qase/Zephyr Scale/Kiwi TCMS). Applies the identical conservative pattern: generic tool name (`tools/import-connector`, `--source=xray`), "Import from Xray" as plain referential UI copy, no Xray logo, `docs/integrations.md` and the Connect screen carry the same disclaimer-footnote treatment. Tracked under the same standing concern issue (#195) as the other four.

**D-X9: In-app entry point — one more array entry, plus a Cloud/Server mode toggle on the Connect screen, the first new UI primitive this family has needed.**
"Import from Xray" is a fifth entry in the same data-driven source list (menu → `/projects/import/xray`, the existing `/projects/import/:source` route, unchanged). Unlike every prior importer (exactly one auth shape each), Xray's Connect screen needs a Cloud/Server toggle at the top that swaps the credential fields below it (Cloud: Client ID, Client Secret, Project Key; Server: Site URL, Personal Access Token, Project Key) — implemented as local component state, no new route or backend concept, matching this project's existing preference for local UI state over premature abstraction.

**D-X10: No mid-job token refresh for Cloud's 24h JWT.**
Confirmed the Cloud token is valid 24 hours. Every prior importer's dry-run-then-import job pair is expected to complete in well under that window (consistent with this project's own job-progress UI design, which assumes tight poll intervals and short-lived jobs, not multi-hour crawls). `NewCloud` authenticates once at client construction and reuses that JWT for the client's whole lifetime; no refresh logic is built. If a future project's Xray Test Repository is large enough to threaten the 24h window, that's a real scaling problem worth its own follow-up, not a v1 concern to design around speculatively.

## Risks / Trade-offs

- **[Risk] Shipping two auth flows and two data-fetch strategies in one change is a materially larger surface than any prior importer in this family (all shipped Cloud-only, or one auth shape).** → Mitigation: D-X1's shared interface keeps `internal/importer`'s mapping logic single and mode-agnostic — the extra surface is contained to `xrayclient`'s two constructors, tested independently (Cloud against `httptest.Server` GraphQL response fixtures, Server/DC against REST response fixtures), not duplicated through the rest of the pipeline.
- **[Risk] No live Xray account (Cloud or Server/DC) is available for real end-to-end verification.** → Mitigation: matches the Zephyr Scale/Kiwi TCMS precedent — verification relies on real-but-wrong-endpoint / real-HTTP-error checks (e.g. pointing Cloud at a fake client_id/secret for a genuine 401, pointing Server/DC's site URL at TestPulse's own app for a genuine connection-refused/404), documented as a stated v1 limitation in `docs/integrations.md`, not silently skipped.
- **[Risk] D-X6's value-shape custom-field fallback for Server/DC could not be verified against a documented Xray-specific field-type API (only Cloud's GraphQL schema was checked in the research pass; Server/DC's own custom-field REST surface, if any, wasn't independently confirmed).** → Mitigation: apply the same fallback to both modes rather than inventing a Server/DC-specific mapping that wasn't verified either — consistent, honestly-scoped behavior across both auth modes beats an unverified asymmetry.
- **[Trade-off] Requiring a PAT (not Basic Auth) for Server/DC means self-hosted Xray instances on Jira versions older than 8.14 (before PAT support) cannot use this importer in v1.** → Accepted: avoiding ever storing a real user's Jira password is a stronger security posture than supporting every possible Jira version: this mirrors the project's existing "never SSO for agents, only scoped tokens" stance (`establish-architecture`) applied to a third-party credential instead of TestPulse's own.
- **[Risk] Documented Cloud rate limits (60-200 calls/min depending on license tier, shared across concurrent users of the same Jira instance) could throttle a large import.** → Mitigation: GraphQL pagination (`limit` 1-100 per page) is implemented as a straightforward page-loop from the start rather than a single unbounded call; explicit backoff/retry-on-429 is left as a follow-up if a real import actually hits the limit, since no importer in this family has needed retry logic yet and speculative retry logic without a real failure to design against would be premature.

## Migration Plan

Additive only, matching the other four importers' shape: no new migration, no new `apps/api` routes, no `packages/shared/openapi.yaml` changes. Everything new lives in `tools/import-connector` and the frontend's existing data-driven source list.

Suggested build sequencing:
1. `tools/import-connector/internal/xrayclient`'s shared `Client` interface and Cloud implementation (`NewCloud`, GraphQL query building, D-X1/D-X2/D-X3) — TDD against `httptest.Server` GraphQL response fixtures built from Xray's own documented schema shapes.
2. `internal/xrayclient`'s Server implementation (`NewServer`, REST calls, D-X2/D-X3) — TDD against `httptest.Server` REST response fixtures.
3. `tools/import-connector/internal/importer` — add the `xray` mapping branch (D-X4/D-X5/D-X6), reusing the existing dry-run/fake-writer test harness; the fake `XrayReader` needs no mode awareness since D-X1 keeps the interface mode-agnostic.
4. `internal/poller`/`cmd/import-connector/main.go` — wire the `mode`-based constructor selection (D-X7).
5. `apps/web`: `ProjectsPage.tsx` source-list entry, `ImportProjectPage.tsx` Xray Connect-screen with the Cloud/Server toggle (D-X9) and both field sets.
6. `e2e/import-connector.spec.ts` — Xray scenarios for the parts reachable without a live account (menu entry, route navigation, mode toggle, Connect form validation for both modes), matching the other four importers' own E2E scope limitation.
7. `docs/integrations.md` — extend with the Xray section (both modes, the PAT-only decision, the stated custom-field limitation); `deploy/compose/docker-compose.yml` and the Helm chart's `import-connector` templates gain an Xray-flavored example; `apps/api/internal/sampledata/seed.go` + its test, per CLAUDE.md's standing Sample-Project-showcase rule.

## Open Questions

- **Whether Server/DC's Test Repository REST endpoints have a `2.0` equivalent** — research consistently found them documented at `1.0` only; worth a direct check against a real Server/DC instance's docs (if the implementer has access) before finalizing the exact paths, but `1.0` is the confirmed-working version either way.
- **Project addressing for the Connect screen**: whether "Project Key" should be validated against Jira's real project-key format before submission, or left as a plain string the importer resolves (and reports an error for) at dry-run time — TestRail/Kiwi TCMS precedent (numeric/plain id, validated only server-side) suggests deferring client-side validation is acceptable for v1.
- **Whether Cucumber-type tests' scenario text should be tagged distinctly in the imported case's description** (e.g. a "Gherkin scenario:" prefix) versus appended plainly like Manual-type's absent-steps fallback — a copy/presentation detail, not a structural decision, left to implementation to match this family's existing description-formatting conventions.
