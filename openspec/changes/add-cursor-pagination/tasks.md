Get user sign-off on the mock before any frontend code below is written.

  **Approved design**: one shared `LoadMoreButton` component (`apps/web/src/components/LoadMoreButton.tsx`) — centered, `variant="outline" size="sm"`, click-triggered (not infinite scroll, which would fight `RunPage`/`FolderExplorerPage`'s keyboard-navigation scrollIntoView), "Load more" copy (no count — cursors carry no total), reusing the app's existing button-internal-spinner loading idiom. Extends the existing `PeoplePage`/`RunsListTriage` "Show N more" idiom rather than inventing a new one. Mock: https://claude.ai/code/artifact/23d4fbdf-a03f-43c9-b3de-39d6cb1bdde9

  **Three product-behavior decisions also approved** (Pepe flagged these as real conflicts, not implementation details, and did not resolve them unilaterally):
  1. `PeoplePage.tsx` currently re-sorts its *entire accumulated* user/team list alphabetically every render, which would make already-rendered rows jump position on every "Load more" click. **Decision: sort each newly-fetched page independently before appending** — the list becomes A→Z blocks that restart per page, never reordering an already-seen row.
  2. `RolesPage.tsx`'s own comment states rank isn't user-facing and the UI always sorts alphabetically — but `GET /roles` now orders by rank tier then insertion order, and an alphabetical resort would fracture tiers across pages. **Decision: drop the client-side resort, trust and display the server's rank-tier order**, reversing that comment's stated behavior. No new tier-header UI.
  3. `RunPage`'s status/assignee filters, `FolderExplorerPage`'s filters/search, and `PeoplePage`'s email search all scan only whatever's been paginated in so far — a filter could silently hide real matches on an unfetched page. **Decision: the moment a filter/search/group-by control is engaged while `nextCursor` is non-null, auto-drain all remaining pages in the background before showing filtered results.** The manual "Load more" button only appears in the default (unfiltered) state.
