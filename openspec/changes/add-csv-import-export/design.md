## Context

TestPulse has two existing "bring data in" paths — neither fits this need. `internal/junitxml`'s `POST /projects/{projectKey}/imports` matches JUnit-XML test *results* onto already-existing cases by key; it can never create a case. `add-testrail-importer`/`add-qase-importer`'s `tools/import-connector` crawls a *remote vendor's own API* asynchronously via a job/poll/progress cycle — architecture built specifically because there's a remote system to talk to and a slow crawl to report progress on. A CSV upload has neither property: the "source" is a file the browser already has in hand, and parsing + creating a few thousand rows is fast, local, synchronous work. This is the first case-creating import that belongs entirely inside `apps/api` itself.

Two existing service methods do almost all the real work already: `Service.BulkAddCases(ctx, projectID, folderID, []domain.CaseContent)` (batch-creates cases, already resolves step-group refs and validates custom field values against the project's real field list) and `domain.CaseContent.Validate()` (the exact validation a normal case-create call would apply: title required, priority/format enum checks). This change is mostly about the CSV row ↔ `CaseContent` mapping layer, not new case-creation logic.

## Goals / Non-Goals

**Goals:**
- Import: upload a CSV, create one TestPulse case per row in a target folder, never abort the whole file over one bad row — report every unimportable row individually (row number + reason), matching the "never silently drop, always name individually" convention `add-testrail-importer`/`add-qase-importer` already established for unmappable custom fields.
- Export: the same fixed column shape, so export → edit in a spreadsheet → re-import is a real, working round-trip.
- Any CSV column that isn't one of the fixed core headers is treated as a project custom field, auto-created as `text` type on first encounter if it doesn't already exist.

**Non-Goals:**
- Structured multi-step cases. A CSV row is fundamentally one record; representing `Step[]` (a one-to-many) would need either a second per-step CSV row-type (a real design commitment few spreadsheet sources already use) or an in-cell delimiter scheme (fragile, ambiguous once a step's own text contains that delimiter). Cases import with the flat `expectedResult` field only, matching how a spreadsheet-native source usually already shapes a "test case" (one row, one expected outcome). A structured-steps CSV shape is a real, separable follow-up if it turns out to matter.
- Run/result export — a reporting/audit use case, not a migration one; a different design problem, not bundled here.
- Matching or updating existing cases by key. Import always creates new cases. Attempting "update in place" would need a key/matching scheme (title? a stable id column round-tripped from a prior export?) that's a real, separate design question — deferred rather than guessed at.
- Excel/`.xlsx`. Every tool in the competitive set (TestRail, Qase, Zephyr, Tuskr, Kiwi TCMS) already exports CSV; `.xlsx` support is a low-risk, additive follow-up once the column-mapping/row-validation logic here is proven, not a blocker to shipping the actual migration path.
- `select`-type custom fields being auto-created from CSV. A CSV value has no attached notion of "this column's set of valid choices" — auto-creating a `select` field would mean guessing the whole option universe from whatever values happen to appear in this one file. Auto-created fields are always `text`; a CSV column that happens to match an *existing* `select`-type field's name is still validated against that field's real option list (D3), and a value that doesn't match one of its options fails that row, reported like any other row-level error — never silently coerced into a new option.

## Decisions

**D1: Synchronous request/response, not the `import_jobs`/poll pattern.**
The `import_jobs` machinery (`add-testrail-importer` D1-D3) exists specifically to let a browser watch a remote, network-latency-bound crawl progress live. A CSV upload has no remote crawl — the whole operation is local parsing plus a handful of database writes, the same cost class as the existing synchronous `POST /projects/{projectKey}/imports` (JUnit-XML). Reusing the async job table for this would add a poll loop and a `tools/import-connector`-shaped deployable for a vendor that doesn't exist. Rejected as solving a latency problem this feature doesn't have. If real-world file sizes turn out to make this slow, that's a future, evidence-driven revisit — not designed against speculatively here.

**D2: New `apps/api/internal/csvcases` package — CSV row ↔ `domain.CaseContent` mapping only, no new case-creation logic.**
`Service.BulkAddCases` already does the actual creation (folder-membership check, step-group-ref resolution, custom-field-value validation, audit logging) — this package's only job is turning CSV rows into `[]domain.CaseContent`, plus the reverse (`[]domain.TestCase` → CSV bytes) for export. Two functions carry the real weight:
- `ParseRows(r io.Reader, existingFields []domain.CustomField) (valid []ParsedRow, problems []RowProblem, newFieldNames []string, err error)` — reads the header row to split fixed-core columns from custom-field columns (any header not in the fixed set, matched case-insensitively); for each data row, maps fixed columns onto `CaseContent`'s fields (`Priority`/`Automated` parsed with a clear per-row error on an invalid value, not a silent default). **Correction, found before implementing**: `CaseContent.CustomFields` is keyed by the field's *id*, not its name (a later field rename must not orphan existing values) — so a CSV column matching an *existing* field is resolved immediately (`text` → the raw value under that field's id; `select` → the raw value looked up against the field's current `Options` by value, storing the matching option's id — a value with no matching option fails that row, exactly like any other row-level problem, never silently coercing a new option). A column matching no existing field can't be resolved to an id yet (it doesn't have one) — its raw value is carried on `ParsedRow.NewValues[headerName]` instead, and the header name is added to `newFieldNames`. Every row calls `content.Validate()` (the exact rule set a normal case-create call already applies); a row that fails — a validation error, or an unresolvable select value — is appended to `problems` with its 1-indexed CSV row number and reason, **not** added to `valid`, and parsing continues to the next row. The caller creates each `newFieldNames` entry as a `text` field (`Service.CreateCustomField`) *before* calling `BulkAddCases`, then merges each row's now-resolvable `NewValues` into its `Content.CustomFields` by the newly-created field's id — new fields are always `text`, so this merge step never faces the select/option-lookup problem `ParseRows` already handled for existing fields.
- `WriteRows(w io.Writer, cases []domain.TestCase, fields []domain.CustomField) error` — the reverse: one row per case, fixed columns first, then one column per `fields` (the project's defined custom fields, in their existing display order). **Correction, found alongside the `ParsedRow` one above**: a `select` field's stored value is an option *id* (same convention as import), not its display text — writing the raw id to the CSV would neither be human-readable nor round-trip back through `ParseRows` (which expects a select column's cell to be the option's display value). `WriteRows` therefore takes the full `[]domain.CustomField` (options included), not bare names, and for a `select` field looks up the case's stored option id against that field's current `Options` to write the matching display value; a `text` field's value is written as-is. A field the case has no value for is a blank cell.

Both built on the standard library's `encoding/csv` — no new dependency, matching `internal/junitxml`'s own precedent of using only the standard library for format parsing.

**D3: New endpoints, synchronous, matching `PermCaseCreate`'s existing create-action gating (no new job/report contract).**
- `POST /api/v1/projects/{projectKey}/cases/import-csv` — multipart file upload (`file` field) plus a `folderId` form field (required — matches `CaseCreateInput.folderId`'s own "explicit, not implicitly root" precedent for a bulk operation, avoiding hundreds of cases landing unexpectedly in a project's root folder). Gated by `requirePermission(domain.PermCaseCreate, projectIDParam)` — the same permission `POST .../cases` already uses, since this is exactly that action performed in bulk. Response body: `{created: int, problems: [{row: int, reason: string}]}` — `problems` is never truncated or collapsed into a count-only summary, mirroring the vendor importers' unmapped-field report.
- `GET /api/v1/projects/{projectKey}/cases/export-csv?folderId={optional}` — streams `text/csv`, gated by the existing read permission (`PermRead`, matching every other project-scoped `GET`). Omitting `folderId` exports the whole project's cases.
Contract-first: `packages/shared/openapi.yaml` gets both paths (import as `multipart/form-data`, matching no existing precedent in this codebase yet — checked, `POST /cases` and the JUnit-XML import are both `application/json`; multipart is new but is the correct, standard shape for a file-upload endpoint, not invented for its own sake) before any handler code, same as every other change.

**D4: Fixed core CSV columns, matching `CaseContent`'s own fields verbatim — no separate "import schema" to design.**
`Title` (required), `Description`, `Expected Result`, `Priority` (`low`/`medium`/`high`/`critical`, case-insensitive, blank = unset), `Tags` (semicolon-separated — commas are reserved for CSV's own cell delimiter, and every competitor's own tag/label export already avoids commas for the same reason), `Platform`, `Test Type`, `Automated` (`true`/`false`/blank, case-insensitive). Header matching is case-insensitive and whitespace-trimmed (`"expected result"`, `"Expected Result"`, `" Expected Result "` all resolve the same column) — a CSV a human exported from a spreadsheet tool is not going to have byte-exact header casing, and rejecting on that would defeat the point of a lowest-common-denominator format.

**D5: Export column order is deterministic and matches import's own column set — the round-trip property is structural, not just documented.**
`WriteRows`'s fixed-column order is identical to `ParseRows`'s recognized header set (D4), and its custom-field columns are the project's `ListCustomFields` order (already a meaningful, user-controlled order — `ReorderCustomFields` exists precisely so this ordering is intentional). A file exported from TestPulse and re-imported unmodified reproduces the same cases (modulo new case ids, an inherent property of "create," not an import bug).

**D6: Every exported cell is passed through a CSV-formula-injection sanitizer — found by automated security review after initial implementation, fixed before this task was marked done.**
`WriteRows` writes several fields verbatim from user-controlled input (a case's `Title`, `Description`, `ExpectedResult`, `Platform`, `TestType`, `Tags`, and every custom field's name and value) — a cell starting with `=`, `+`, `-`, `@`, tab, or CR is interpreted as a formula by Excel/Google Sheets/LibreOffice on open (CWE-1236), not a theoretical risk given this feature's whole purpose is producing files real users open in real spreadsheet tools. A failing regression test was written first, confirmed red against the unsanitized code, then `sanitizeCSVCell` (prefixes an affected cell with a single quote, the standard mitigation — every affected application then treats the cell as plain text) applied to every written cell (header and data both, since a custom field's own name is equally user-controlled) before writing.

## Risks / Trade-offs

- **[Risk] A very large CSV (tens of thousands of rows) makes the synchronous request slow, unlike a job the browser can poll.** → Mitigation: accepted for v1 given D1's reasoning (no evidence this is a real-world size yet, and the existing global request-body size limit — `harden(api)#164` — already bounds worst-case abuse). If real usage proves this wrong, the response is a well-understood one (chunked/streamed row processing or a move to the job pattern), not a redesign of the column-mapping logic in `internal/csvcases`.
- **[Risk] A CSV column header that's a near-miss of a fixed-core name (e.g. `"Expected Results"` plural) silently becomes a new custom field instead of an error.** → Mitigation: this is the same trade-off TestRail/Qase's own custom-field mapping accepts (an unrecognized field is reported, not guessed at) — a spurious `"Expected Results"` custom field is visible in the created-fields list and in the import report, not silently lost data, and is a one-click fix (rename the CSV header, re-import) rather than a data-loss failure mode.
- **[Trade-off] `select`-type custom fields can never be created purely from a CSV import (Non-Goals).** → Accepted: the alternative (auto-inferring a select field's option universe from one file's observed values) is guesswork this design deliberately avoids; a Tenant/Project Admin who wants a `select` field defines it once in the UI first, then CSV values matching its options import cleanly (D2's last bullet).

## Migration Plan

Additive only — two new endpoints, one new package, no schema/migration changes (no new table; cases created via CSV are ordinary cases through the existing `CreateBatch` store path). No rollback complexity beyond removing the new routes.

Suggested build sequencing:
1. `packages/shared/openapi.yaml` — `import-csv`/`export-csv` paths and their request/response schemas, then `make generate`.
2. `apps/api/internal/csvcases` — `ParseRows`/`WriteRows`, TDD against `domain.CaseContent`/`domain.TestCase` directly (no HTTP layer needed for these tests).
3. `apps/api/internal/server` — the two handlers, wired to `Service.CreateCustomField` (for new field names) + `Service.BulkAddCases` (import) and `Service.ListCases` (export, filtered by `folderId` when present).
4. A Pepe UX pass for the entry points (Library toolbar "Export," and where "Import from CSV" lives relative to the existing "+ New project" source menu — a Library-level import, unlike the vendor importers, isn't inherently a *project-creation* action, so it may belong as its own Library-toolbar affordance rather than joining `newProjectSources`) — **required before any frontend code is written**, per standing practice. Not designed here; this document covers the contract, not the pixels.
5. Frontend implementation per the approved mock.
6. `docs/testing.md` or `docs/integrations.md` (whichever the docs-reviewer persona judges the better fit — this isn't a "connector," so `integrations.md`'s framing may not apply) — a "CSV import/export" section: the fixed column table, the custom-field-auto-creation rule, the non-goals stated plainly (no steps, no update-by-key, no `.xlsx` yet).
7. Sample Project: seed.go gets either a tiny bundled CSV fixture demonstrating import, or (simpler, and enough to showcase the feature) relies on its existing seeded cases to demonstrate the Export action — decide during implementation, but do one of the two; this feature has no "no live account to connect to" excuse the vendor importers have.
