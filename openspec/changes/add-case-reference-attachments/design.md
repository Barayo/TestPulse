## Context

Run results already support evidence attachments (`add-run-item-screenshot-attachments`): a `result_attachments` table keyed by `run_item_id`/`result_id`, an `attachmentimage` package validating JPEG/PNG/WebP via `image.DecodeConfig` (5MB cap, never decoded/transformed beyond that), a `Service`/`AttachmentRepo` pair, and `/items/{itemID}/attachments`, `/results/{resultID}/attachments`, `/attachments/{attachmentID}` routes gated by `runRecordResult`/`read`.

That mechanism is deliberately scoped to execution *evidence* — it's tied to a run item/result, which only exists once a run exists. Reference material (a screenshot of the UI under test, a design mock, a spec document) belongs to the case's own definition and needs to exist independent of any run ever having happened.

Cases are versioned: `TestCase` holds an identity (`ID`, `Key`) plus a `CurrentVersion`/`Content` pointer, and every edit creates an immutable `CaseVersion` row. Some case-level data is explicitly *not* versioned content — `JiraIssueKey`/`JiraIssueSummary`/etc. are identity-level metadata set via their own endpoint, independent of the content-edit endpoint, precisely because a Jira link isn't part of what a specific version's content snapshot means.

## Goals / Non-Goals

**Goals:**
- Let a case author attach images, PDFs, and plain-text files (.txt/.log) to a case, visible to anyone viewing any version of that case — including anonymous visitors to a public project, consistent with the rest of a case's content already being public (D7).
- Reuse the proven run-result-attachments shape (dedicated table, validate-then-store, serve-by-id-with-ETag) rather than inventing a new pattern.
- Keep case attachments and run-result attachments fully independent — different table, different repo, different routes, different ids — so neither capability's queries or permission checks have to reason about the other's rows.

**Non-Goals:**
- Attachments are not versioned content and are not reconstructed/snapshotted per `CaseVersion` — attaching or removing a file is not a case edit and does not bump `CurrentVersion` or appear in version history/diffs.
- No in-browser PDF preview/rendering, and no generated thumbnails of any kind (considered and explicitly rejected — see below) — every non-image attachment (PDF, .txt, .log) renders as a filename + file-type icon and links out to `GET /case-attachments/{id}` (served with `Content-Disposition: inline` for PDFs, or as a normal response otherwise), the same "browser decides" treatment already used for anything-not-an-image today.
- No arbitrary file types (docs, zips, etc.) — scope is images + PDF + plain text per the file-type decision below.
- No migration of existing run-result attachments into this mechanism.
- No client-side-generated PDF thumbnail previews. Considered mid-implementation (render page 1 via `pdf.js` in-browser at upload time, store the PNG alongside the PDF): rejected as out of scope for this change — it would add a `pdfjs-dist` frontend dependency, a new stored-thumbnail column/endpoint, and revisit every backend layer already built and tested. Server-side rendering was ruled out entirely: Go has no mature pure-library PDF rasterizer, and the realistic alternatives (CGO bindings to poppler/mupdf, or shelling out to `pdftoppm`/`mutool`) conflict with the project's distroless, multi-arch (amd64+arm64) image constraint. Tracked as a separate backlog idea, not part of this change.

## Decisions

**D1 — Attach to the case identity, not a `CaseVersion` snapshot.** A `case_attachments` row references `case_id` (not `case_id + version`). Rationale: reference material describes "the thing being tested," which doesn't change meaning when the case's steps get edited — the same reasoning that already keeps `JiraIssueKey` outside the versioned `CaseContent`. Alternative considered: snapshot attachments per version (mirrors how `Step.GroupRef` snapshots a `StepGroup` at save time). Rejected — that pattern exists because step-group *content* can drift and a past version must stay reproducible; attachments aren't part of reproducing what a version asserted, they're supporting context, so forcing re-attachment on every edit would be pure friction with no corresponding benefit.

**D2 — New `attachmentfile` package, not a modified `attachmentimage`.** `attachmentimage.ValidateUpload` returns an error for anything `image.DecodeConfig` can't parse — a valid PDF or text file would always fail. Add `apps/api/internal/attachmentfile` with `ValidateUpload(data []byte) (contentType string, err error)` that: (a) enforces the same `5*1024*1024` byte cap, (b) delegates to `attachmentimage.ValidateUpload` for the three image formats, (c) falls back to a PDF check via `bytes.HasPrefix(data, []byte("%PDF-"))` (the standard PDF magic header), (d) falls back further to a plain-text heuristic — valid UTF-8 with no NUL byte — returning `text/plain` for both `.txt` and `.log` uploads alike. There's no magic header for plain text the way there is for images/PDF, so this heuristic (the same one a `file` command or browser uses) is the closest equivalent; it deliberately stays filename-agnostic, matching `attachmentimage`'s existing content-only-sniffing policy, rather than trusting a client-supplied extension. No PDF parsing/rendering library, no text reformatting — the content type is just trusted once the respective check matches, exactly as little work as the image path does (no decode, no transform). `attachmentimage` itself is untouched; `attachmentfile` depends on it rather than the reverse, so run-result attachments keep their narrower image-only contract.

**D3 — Separate table, repo, and routes; no shared `attachments` table.** New `case_attachments` table: `id, case_id, filename, content_type, image bytea, created_at` (no `result_id`/staging concept — case attachments are never "staged" against a pending verdict, they're just created). New `CaseAttachmentRepo` in `store`, new `Service.AttachCaseFile/ListCaseAttachments/GetCaseAttachment/DeleteCaseAttachment`, new routes:
  - `GET/POST /cases/{caseKey}/attachments` (list / upload, under the existing `/cases/{caseKey}` route group, reusing its `resolveKey` case-id resolution)
  - `GET/DELETE /case-attachments/{attachmentID}` (serve / delete — named `case-attachments` rather than reusing `/attachments/{attachmentID}` so the two id spaces, and their distinct `ProjectIDFor*` resolvers, never have to disambiguate which table an id belongs to)

  Alternative considered: generalize `result_attachments` into a polymorphic table (`owner_type`, `owner_id`). Rejected — the existing table's `run_item_id`/`result_id` pair and staging semantics (`result_id IS NULL` = staged) are specific to the run-result lifecycle; bolting a second owner concept onto it would make every existing query there need an extra discriminator for no shared behavior (case attachments have no staging state, no "linked to a result" transition).

**D4 — Permissions mirror case content, not run attachments.** Upload/delete require `caseEdit` (same as editing a case's own content); viewing/downloading requires `read` (same as viewing the case). `caseDelete` is not involved — removing one attachment isn't deleting the case. This differs from run-result attachments (`runRecordResult`-gated) because the resource being modified is the case, not a run.

**D5 — File type scope: images + PDF + plain text (.txt/.log), 5MB cap.** Per product decision: covers the issue's three examples (screenshot, design mock → image; spec document → PDF) plus `.txt`/`.log` (common for attaching manual-test notes or a captured CI log), without taking on fully arbitrary-file risk (no content validation possible, XSS-via-served-file surface for binary formats). Same 5MB ceiling as run-result attachments — no stated reason for case references to need to be larger, and it bounds `case_attachments` table growth the same way.

**D6 — Serving: same ETag/Cache-Control pattern as `getAttachment`, with one addition.** `GET /case-attachments/{id}` reuses the existing immutable-content ETag approach (`"{createdAt-unixnano-base36}"`, `Cache-Control: private, max-age=3600`, `If-None-Match` → 304). For PDFs, additionally set `Content-Disposition: inline; filename="..."` (browsers render PDFs inline by default when `Content-Type: application/pdf` and disposition is `inline`; images already render inline via `<img>` regardless of disposition, and `text/plain` renders inline by default with no header needed, so this header is a no-op for both) — filename uses the stored `Filename`, sanitized the same way `csv_handlers.go` already quotes a `Content-Disposition` filename.

**D7 — Public projects expose case attachments, via the same handler-reuse pattern as every other public case route.** Per product decision: `GET /public/cases/{caseKey}/attachments` and `GET /public/case-attachments/{id}` are added to `mountPublicAPI` (`public_handlers.go`), calling the exact same `listCaseAttachments`/`getCaseAttachment` handlers as the authenticated routes, just swapping `requirePermission` for `requirePublicProject` — identical to how `getCase`/`listCaseVersions`/`listCaseExecutions` are already exposed publicly. Write operations (upload/delete) are never exposed publicly, matching every other public route. Rationale: an anonymous visitor to a public project can already see a case's full content, version history, and execution history; withholding reference attachments alone would be an arbitrary, inconsistent gap in what "public" means for a case.

## Risks / Trade-offs

- **[Risk]** A PDF is accepted on nothing more than its magic header — a file that merely starts with `%PDF-` but is otherwise malformed, or carries active content (embedded JS, launch actions), is stored and served back `inline` on the API origin, where a browser's built-in PDF viewer renders it. → **Mitigation**: `X-Content-Type-Options: nosniff` is already set globally (security-headers middleware), so the response is never sniffed as something else; additionally, `getCaseAttachment` overrides the global CSP with `Content-Security-Policy: sandbox; default-src 'none'` specifically when serving a PDF — the `sandbox` directive disables script execution, forms, and popups for that response and treats it as a unique (cookieless) origin, so even a malicious PDF gains no access to the API origin's session. Images keep the same trust level as before (`attachmentimage` doesn't verify well-formedness beyond `DecodeConfig` either) since they carry no equivalent active-content risk.
- **[Risk]** `case_attachments` has no project id column, same as `result_attachments` — `ProjectIDForCaseAttachment` must join through `case_attachments → test_cases → projects`, an extra join on every permission check. → **Mitigation**: identical cost/shape to the existing `AttachmentRepo.ProjectID`'s three-table join; not a new pattern, not a measurable regression at current scale.
- **[Trade-off]** Attachments aren't versioned, so deleting one is a silent, un-audited-in-version-history change to what a case "shows." → **Mitigation**: `Service.DeleteCaseAttachment` still calls `s.audit(...)`, so it's visible in the project activity log even though it's not a `CaseVersion` entry — consistent with how `JiraIssueKey` changes are audited but not versioned.

## Migration Plan

Additive only: new migration `000NN_case_attachments.sql` creates `case_attachments`; no existing table is altered. No backfill — existing cases simply start with zero attachments. Rollback is deleting the new migration file's effect via a fresh down-equivalent migration if ever needed (project policy: migrations are never edited in place once shipped).

## Open Questions

None outstanding — file-type scope (images + PDF + plain text), PDF-thumbnail scope (rejected, see Non-Goals), and public-project visibility (D7) were all confirmed during implementation.
