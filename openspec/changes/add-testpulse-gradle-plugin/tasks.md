## 3. Attachments: class-level allowlist and invocation-unique storage (test-first)

- [x] 3.1 Write a failing unit test: `TestPulseAttachments.attach("LOGIN-42", bytes, "failure.png", "image/png")` called from a class where a method carries `@TestPulse(caseKey = "LOGIN-42")` succeeds and writes a sidecar into the scratch directory; implement `attach()` using `StackWalker` to identify the calling class and reflection to collect that class's own `@TestPulse` case keys, until green
- [x] 3.2 Write a failing unit test: `attach("OTHER-1", ...)` called from a class whose `@TestPulse`-annotated methods only declare other case keys throws, and writes nothing; implement the allowlist rejection until green
- [x] 3.3 Write a failing unit test: content-type validation (`image/png`/`image/jpeg`/`image/webp` only) runs and rejects before the allowlist check would otherwise accept a call, so an unsupported content type is rejected even for a valid case key; implement the ordering until green
- [x] 3.4 Write a failing unit test: two `attach()` calls under the same case key (simulating two invocations of a parameterized test) both produce distinct sidecar files, neither overwriting the other; implement invocation-unique filenames (`hash(caseKey + a freshly-generated UUID)`) until green
- [x] 3.5 (folded into AttachmentStoreTest's own coverage) `AttachmentStore.readAll` already returns both sidecars sharing a case key as separate entries (verified by `twoAttachmentsUnderTheSameCaseKeyBothSurvive`); `testpulseSubmit`'s own grouping-into-the-request-array happens in task group 5, since it needs the submitter code to exist first
- [x] 3.6 Write a failing Gradle TestKit integration test: a real project with a test that calls `attach()` under a case key belonging to a *different* class's `@TestPulse` annotation, run the build, assert it fails with the allowlist rejection message — proving the check works against real compiled classes and real `StackWalker` behavior, not just mocked reflection
- [x] 3.7 Write a failing Gradle TestKit integration test: a real `@ParameterizedTest` calling `attach()` multiple times under the same case key, run the build, assert all attachments are present in the scratch directory afterward (not just one) — **real gap found and fixed via these two tests**: (a) applying the plugin only puts its jar on the buildscript classpath, not the consumer's own `src/test/java` compile classpath, so `TestPulseAttachments` wasn't visible to test code at all — fixed by having the plugin add its own backing jar as a `testImplementation` file dependency automatically; (b) that fix then exposed that `AttachmentStore` depended on Jackson (an `implementation`-scoped dependency of the plugin's own buildscript, which doesn't propagate through a raw file dependency, no transitive metadata) — fixed by dropping the JSON dependency entirely for the 3-field attachment metadata format (plain one-field-per-line text) since it runs in consumer-controlled forked test JVMs, not just the plugin's own daemon-side code. Also surfaced and fixed a related staleness gap: nothing cleared `build/testpulse/attachments/` between runs, so a stale prior run's attachments could leak into a later submission — fixed via `Test.doFirst` clearing the scratch dir exactly once per run (the Gradle-task equivalent of testpulse-jest's `onRunStart`), covered by a new `ScratchDirCleanupFunctionalTest`
