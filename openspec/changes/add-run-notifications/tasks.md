## 12. Security review (Luis)

- [x] 12.1 Dispatch Luis to review the SSRF mitigation (URL validation against localhost/private/link-local ranges) specifically — this is the one part of this change with real security surface per design.md's Risks section. Confirm the validation can't be bypassed via DNS rebinding, IPv6 loopback/private forms, or a redirect from an initially-valid URL to an internal one (decide during review whether redirect-following needs to be disabled on the outbound HTTP client). **Findings (with live PoCs, not just source reading):** (1) MUST FIX — `ValidateWebhookURL` never resolved DNS at all for hostname-form destinations; an attacker with ordinary `manageProject` could point any domain's A record straight at an internal address (e.g. `169.254.169.254`) and it would validate and deliver on the first failed/blocked result, no rebinding TOCTOU needed — broader than the design.md's "DNS rebinding" framing suggested. (2) MUST FIX — `webhookHTTPClient` had no `CheckRedirect`, so Go's default (follow up to 10 redirects) applied; Luis reproduced live a public destination 302-redirecting delivery to a second, "internal" `httptest.Server`, which received the forwarded request — a complete bypass of `ValidateWebhookURL` requiring zero DNS control. (3) MUST FIX — the `"localhost"` check was a case-sensitive exact string match; `https://LOCALHOST/...` and `https://localhost./...` (trailing-dot FQDN) sailed through, confirmed via `url.Parse(...).Hostname()` preserving case/dot. (4) SHOULD FIX — both call sites invoke `dispatchWebhooks` synchronously on the request goroutine with a sequential per-destination loop; a project with 3 slow/dead destinations blocks `RecordResult`/`CloseRun` for up to ~9s, violating design.md D4's "never blocks the write" guarantee for the multi-destination case (single-destination case already had a passing regression test, which is why this wasn't caught). (5) LOW-RISK, not exploitable in TestPulse's actual deployment — decimal/octal/hex numeric IP literals (e.g. `2130706433` for `127.0.0.1`) bypass `net.ParseIP`; Luis verified live that these *do* resolve to loopback with a cgo/glibc-style resolver, but rebuilt the same test with `CGO_ENABLED=0` (matching `Dockerfile`'s actual distroless build) and confirmed Go's pure-Go resolver fails to resolve them (`no such host`) — not reachable in prod, but fragile to leave as an implicit, unintentional control. Ruled out with no finding: IPv6 loopback/unspecified forms and IPv4-mapped-IPv6 were already handled correctly by `net.IP`'s `Is*` methods; no response-body resource-exhaustion vector (body was never read, only closed).
- [x] 12.2 Address any findings; re-run the full verification sweep (group 11) if anything changes. **Fixed all five findings in `apps/api/internal/service/webhooks.go` and its two call sites in `service.go`:** replaced the config-time-only literal-IP/string check with a dial-time IP check — `webhookHTTPClient`'s `Transport.DialContext` (`dialWebhookDestination`) now resolves the hostname via `net.DefaultResolver.LookupIPAddr` and rejects any resolved IP that's loopback/private/link-local/unspecified *at the point of actually connecting*, which closes #1 and #5 (any resolved form, however encoded, hits the same IP-level check) and, combined with `CheckRedirect: func(...) error { return http.ErrUseLastResponse }` refusing all redirects outright, closes #2 (the dial hook also re-runs on every would-be redirect hop, but redirects are refused before that matters). `ValidateWebhookURL` (config-time UX check) was fixed for #3 by lowercasing and trailing-dot-trimming the hostname before the `"localhost"` comparison, and now documents that the dial-time check, not itself, is the real security boundary.
