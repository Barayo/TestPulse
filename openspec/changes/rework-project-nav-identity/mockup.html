Proposal A

The Fused Chip

Problem it solves

Replaces the wordmark → "›" → bold name → floating arrow-icon chain with a single rounded chip: a small colored initial-avatar, the project name, and a chevron — one visual unit with one shared hover/focus state, instead of two disconnected controls sitting next to each other.

Interaction

The entire chip is one <button>. Hover tints the whole chip (background, not just an underline on the text). Click opens the same centered search dialog the app already has today — smallest change to the overlay mechanism, so this is the lowest-risk option.

Keyboard · frequency fit

Tab lands on the chip as one stop; Enter/Space opens the dialog. ⌘K works from anywhere. Switching is rare, so a small centered dialog (not a persistent panel) is proportionate — it costs nothing when closed and doesn't linger. With 0–1 projects the chip sheds its avatar, pill background and chevron entirely, becoming plain static text — not a disabled-looking control.

      Proposal B

      The Breadcrumb Rail

      Problem it solves

      The old bold 20px name read as a second brand element competing with the wordmark. Restyled at breadcrumb scale (mono, uppercase, tracked — the exact voice already used by Breadcrumbs.tsx), it now reads as a continuation of "where am I", not a peer to "TestPulse".

      Interaction

      The name + inline caret is one clickable crumb. Click opens a compact dropdown anchored right under the crumb — search plus a small 2-up card grid. (Revised: an earlier version of this proposal spanned the full header width as a mega-menu; that was more visual investment than a rarely-used control earns, so it's now sized like an ordinary dropdown instead.)

      Keyboard · frequency fit

      Tab reaches the crumb as one stop; Enter/Space opens the panel, first search focus is automatic. ⌘K works globally. Single-project mode drops the caret and renders genuinely plain text — same color/weight as the last (current) breadcrumb segment today, no hover feedback at all.

        Proposal C

        The Anchored Popover

        Problem it solves

        Keeps the name's current visual weight (it's still the only persistent "where am I" signal on non-landing pages) but removes the separate icon-button entirely — a small caret is fused directly onto the name itself, so there is exactly one click target where there used to be two.

        Interaction

        Click the name+caret to open a small card popover anchored right under it (with a connecting pointer), not a centered modal — visually "attached" to the thing you clicked, like Notion/Linear workspace switchers, rather than a dialog that appears in the middle of the screen.

        Keyboard · frequency fit

        Tab reaches the fused name+caret as one stop; Enter/Space opens it, search auto-focuses. ⌘K works globally. Of the three, this adds the least persistent visual weight in its resting state (no avatar, no pill background — just a small caret) for a control used rarely. With 0–1 projects the caret disappears and the name becomes genuinely plain static text — no hover feedback at all.

            Recommendation

            The system: one non-redundant division of labor, not a page-by-page patch

            The division of labor

            Top bar = which project, persistently, on every project-scoped page — and it owns the "Projects" home entry point too (the wordmark already links there), so nothing downstream should repeat it. Breadcrumb = only the real, unique, clickable nodes between project and current page; it drops the leading "Projects › {Project}" pair always (top bar's job) and drops a trailing segment whenever it's identical to the page's own h1 (page's job) — what survives, if anything, is shown. H1 = the one definitive label for current location, never echoed by the other two.

            Why not just delete Breadcrumbs.tsx

            Checked against every real page type, not just the two originally simulated: on Suites/Runs, trimming both ends leaves nothing (matches the mockup's now-empty Suites state). On Suite/Case detail, trimming the lead leaves a real ancestor link ("Suites", "Library › folder…") the top bar and h1 don't cover — deleted entirely, that link is gone with no replacement. Folder Explorer's deep-nesting "…" collapse is untouched by this — only its redundant lead trims away. The rule is "trim the redundant ends," not "remove the component."

            Landing page: relocate, don't hide-and-lose

            The earlier in-flight fix hid the top-bar control outright on landing and, with it, silently removed the only discoverable way to switch from that page — a real regression, correctly caught. The actual fix: the switcher isn't a second thing living next to the name anymore, it's fused onto the h1 itself (a small chevron after "Sample Project"). One instance of the name, one click target, ⌘K still works everywhere. Shared across all three proposals — this piece isn't about which top-bar idiom wins.

            One loose end for real implementation

            Breadcrumbs.tsx currently bails out (renders nothing) whenever segments.length <= 1, written for the old always-3-segment input where a lone segment was guaranteed to just repeat the h1. Once callers pass already-trimmed segments, a length-1 result (e.g. Suite detail's "Suites") is a real link, not noise — that guard needs a small follow-up so it doesn't also eat the one case worth keeping.

            Pick, among A/B/C

            C (Anchored Popover) is still the best fit for the persistent top-bar control itself: least resting chrome, proportionate open state. That verdict is orthogonal to everything above — the breadcrumb/h1 fix applies identically regardless of which proposal wins.
